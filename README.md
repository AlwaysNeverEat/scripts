# Tampermonkey Scripts + Oil Calculator Cars DB

Экосистема калькулятора масел: юзерскрипты для сайтов подбора + общая база
рассчитанных машин (backend + сайт).

## Целевая архитектура

**`shared/` — единственный источник правды** для каталога масел (`oils.js`,
включая прайс), логики подбора (`calculator.js`), разбора допусков
(`approvals.js`) и текстового отчёта (`report.js`).

### Подбор по допускам

Поле `car_approvals` — это НЕ требования машины: источник отдаёт паспорт
рекомендованного масла целиком, поэтому в списке в среднем 28.6 строк, из них
69% — допуски чужих марок, а у 66.5% машин список физически противоречив сам
себе. `shared/approvals.js` разбирает каждую строку на физику (зольность,
HTHS, вязкость, интервал), сверяет с маркой машины и с рекомендацией Motul по
этой же модификации, и оставляет в среднем 4.6 действительно решающих допуска.
Вес допуска в скоринге = цена ошибки по нему; чужие марки весят ноль.

Ограничения накладываются только там, где для них есть физическая причина:
по золе — если у мотора есть сажевый фильтр (дизель с 2009 г., бензин с
2018 г.), по густоте — если завод для этого мотора не одобрял масло жиже ни в
одном из своих допусков.

Полный разбор с обоснованием весов и списком того, на что можно закрыть
глаза, — **[docs/DOPUSKI.md](docs/DOPUSKI.md)**.

Корневой `Mann + Motul Oil Calculator-2.12.user.js` — **собираемый артефакт**:
генерируется из `shared/` + `userscript/src/` (site-glue: парсеры сайтов,
виджет, GM_*). Руками его не редактировать.

**Как обновить прайс/каталог масел:** отредактировать `shared/oils.js`
(можно прямо в веб-интерфейсе GitHub) → после пуша в `main` GitHub Action
`build-userscripts` сам пересоберёт `.user.js` с новым номером версии, и
Tampermonkey у всех установивших подтянет обновление по `@updateURL`.

Локальная сборка и тесты:

```bash
npm install
npm test                  # паритетные тесты отчёта и HTML виджета
npm run build:userscript  # пересобрать корневой .user.js
```

> Историческая справка: логика в `shared/` была извлечена из юзерскрипта для
> сайта, но юзерскрипт продолжал жить со своей встроенной копией — из-за этого
> прайс приходилось обновлять в нескольких файлах. Сборка из `shared/`
> устраняет это.

## Записи — клон-обложка админки ZMS

Страница `/records.html` — полноценная обёртка над оригинальной админкой
записей `zamena-masla-spot.ru/admin/record`, переживающая её падения.

**Как работает.** Бэкенд раз в минуту (env `RECORDS_SYNC_INTERVAL_MS`,
минимум 10 с) заходит в оригинал под общими кредами, парсит HTML доски
(`shared/crmRecords.js`) на сегодня и завтра (МСК) и кладёт снапшоты в
`record_snapshots`. Страница читает кеш, показывает «обновлено N назад»; если
оригинал лежит — баннер + все изменения копятся в очереди `record_ops` и
проталкиваются автоматически после восстановления (порядок сохраняется,
конфликт «слот уже занят» помечает операцию failed с причиной).

**Длинные записи переносятся целиком или никак.** Длинная («продлённая»)
запись в оригинале — это N отдельных получасовых записей, транзакций у него
нет, поэтому перенос червячка = N POST'ов подряд. Ход операции пишется в
`record_ops.progress` (`backend/src/records/opEngine.js`, тесты —
`opEngine.test.js`):

- перед переносом целевое окно проверяется по **свежей** доске дня назначения
  — пока операция ждала в очереди, слот мог занять кто угодно; свои же слоты
  (сдвиг внутри той же станции) занятыми не считаются;
- оригинал лёг посреди хвостов — операция остаётся pending и продолжается с
  того же места после восстановления (повторный POST идемпотентен), а не
  начинает заново;
- окно заняли, запись исчезла, оригинал молча не сохранил хвост или кончились
  попытки — уже уехавшие слоты **возвращаются на прежние места** (по `from`,
  который присылает фронт), операция становится failed с причиной, и в очереди
  появляется кнопка «другое время», открывающая перенос заново. Половина
  записи в новом месте не остаётся никогда;
- то же и для создания длинной записи: недосозданные слоты удаляются (только
  свои — чужие записи в тех же боксах не трогаются). Единственная операция без
  отката — удаление: воскресить запись нельзя, поэтому прогресс там нужен лишь
  чтобы ретрай не ходил по уже удалённым слотам.

**История очереди живёт сутки:** применённые (done/failed) операции воркер
удаляет раз в час, незавершённые не трогает никогда, сколько бы они ни ждали
живого оригинала.

**Доступ.** Без аккаунтов сайта: кто-то один вводит логин/пароль оригинальной
админки (форма появляется сама), сервер хранит их в `zms_records_config`,
сам перелогинивается и страница работает у всех. Пароль сменили — любой
вводит новый по кнопке с ключом.

**Что умеет UI** (только SVG-иконки, тёмная тема сайта):
- обзор всех станций с мини-полосой занятости; поиск по имени/цифрам
  телефона/адресу; порядок карточек переключается над сеткой — «как на доске»
  (по линии метро, внутри линии по алфавиту), «по алфавиту» одним списком и
  «по метро» столбиками линий в их цветах; выбор помнится между заходами
  (`localStorage`, ключ `zm_records_sort`);
- вид станции: дорожек столько, сколько боксов (2 у двухбоксовых, 3 у
  Оптиков 2); продлённые записи (одно имя, слоты встык, телефон-заглушка
  `+71111111111` у продолжений) рисуются одним «червячком» с насечками;
- запись сразу на 30 мин–3 ч с графическим превью занимаемых слотов
  (первый слот — настоящая запись, остальные — продолжения, как в
  оригинальном скрипте «Продлить запись»);
- «Перенести всю запись» одним действием (весь червячок, с подсветкой окон
  нужной длины на любой станции/дне), продление, умное удаление с
  чекбоксами цепочки, копирование строки записи, правка имени/телефона
  (госномер и комментарий при переносе не затираются — бэкенд дочитывает их
  из формы редактирования);
- в открытой записи видно госномер и комментарий: на доске оригинала их нет,
  поэтому окно тянет карточку отдельным запросом (`GET /api/records/record/:id`
  → та же форма редактирования) и показывает, пока она едет, что она едет.
  Эти же значения подставляются в поля «Изменить данные», так что комментарий
  можно не только прочитать, но и осознанно очистить;
- карта станций (Leaflet из бандла + бесплатные тайлы CARTO): плашки с
  названиями, цветом линии метро и счётчиком записей; поиск по улице через
  Nominatim показывает ближайшие станции с расстоянием; мини-карта прямо в
  окне создания — клиент передумал, адрес меняется кликом, введённые данные
  сохраняются;
- очередь операций видна отдельным окном: pending можно отменить (уже уехавшая
  часть при этом вернётся на место), у сорвавшегося переноса есть кнопка
  «другое время», призраки отложенных записей рисуются на сетке пунктиром.

**Права модератора в разделе.** Записываться, переносить и удалять может кто
угодно, в том числе без аккаунта сайта, — а вот две вещи закрыты ролью `mod`
(или `admin`), причём на сервере, а не скрытой кнопкой:

- **логин/пароль оригинальной админки.** Кнопка с ключом видна только
  модератору, `POST /api/records/credentials` принимает только от него.
  Неверная пара рвёт раздел сразу у всех, поэтому вводит её тот, кто отвечает.
  Пока кредов нет вообще, форму видит модератор, а остальные — объяснение,
  чего ждать и от кого;
- **карточка станции.** Справочник станций лежит в коде
  (`shared/stationsMeta.js`), но ворота перевешивают, гидростойку ставят,
  кондиционер снимают — и ждать релиза ради строчки незачем. Кнопка «Изменить»
  на станции открывает форму: код перевода звонка, метро и линия, конфигурация,
  высота ворот, гидростойка, заправка кондиционера, число боксов, заметка.
  Заполненные поля ложатся в `station_overrides.patch` (миграция `022`) и
  накатываются поверх справочника при чтении — пустое поле означает «как в
  коде», поэтому правка `stationsMeta.js` продолжает работать для всего
  остального (тесты — `shared/stationsMeta.test.js`). Правку видят все и
  везде, где станция вообще названа: карточки обзора, вид станции, плашки на
  карте, подсказка «ближайшие станции». Алиасы справочника («Мурино» =
  «Охтинская») делят один ключ `short`, то есть и одну правку. Кнопка
  «Сбросить» удаляет строку целиком — станция возвращается к коду.

**Предупреждение по станции.** Там же, отдельным полем: «заправка кондея не
работает». Ставит модератор, видят все — на карточке станции в обзоре (плюс
рамка в цвет предупреждения), над расписанием станции и в окне новой записи и
переноса, то есть до того, как что-то пообещали клиенту. Предупреждение
доезжает до чужих вкладок само (перечитывается тем же тиком, что и доска, раз
в 45 секунд), а снимается пустым полем.

**Топ по записям (месячный).** Каждая успешно созданная запись даёт автору
одну строку в `record_credits` (миграция `020`), и вкладка «Топ» на сайте
показывает рейтинг за текущий месяц (МСК):

- одна запись = один балл независимо от длины: длинная запись — это одна
  операция создания, сколько бы получасовых слотов она ни заняла;
- **продление уже существующей записи не считается** — слоты-продолжения
  создаются с телефоном-заглушкой (`isExtensionCreate()` в
  `shared/crmRecords.js`), продлённая запись остаётся одной записью;
- переносы, правки и удаления новых очков не дают — это работа с уже сделанной
  записью; **удаление записи очко и не снимает**: зачёт выдаётся один раз и не
  отзывается (клиент отменился — работа всё равно была сделана);
- 1-го числа рейтинг начинается с нуля (выборка идёт по текущему `YYYY-MM`),
  а над списком появляется карточка «Топ в прошлом месяце» с тем, кто был
  первым к концу месяца — прошлые зачёты никуда не удаляются;
- автор берётся из сессии сайта (`optionalSession` на `/api/records`), а не из
  тела запроса — подписаться чужим именем нельзя. Гость записи делать может,
  просто в топ они не попадут.

Счётчик живёт отдельной таблицей, а не считается по `record_ops`: история
очереди чистится через сутки, а месяц должен дожить до конца.

**Лента активности в профиле («квадратики» как на GitHub).** Те же
`record_credits`, только в разрезе дней: год клеток, колонка — неделя (Пн…Вс),
наведение (на телефоне — тап) показывает «3 записи · 4 августа 2026». Видна и в
своём профиле, и в чужом (`GET /api/profile/activity`, `GET
/api/users/:id/activity`, индекс из миграции `023`).

Яркость клетки считается **от среднего**, а не от абсолютных чисел: среднее
берётся по активным дням (где записи были), день ровно на среднем — середина
шкалы, полтора средних и выше — максимум (`activityLevel()` в
`shared/activityHeatmap.js`). Так лента одинаково читается и у того, кто делает
три записи в день, и у того, кто делает тридцать; выходные и отпуска планку не
занижают. Под сеткой подписано, от какого среднего она посчитана, — иначе цвет
выглядел бы произволом. Сетку строит общий модуль, поэтому порядок дней у
бэкенда и фронта совпадает до клетки; день — в МСК, как и месяц зачёта.

**Справочник станций** — `shared/stationsMeta.js` (метро/линия/боксы/высота
ворот/гидростойка/заправка кондиционера + код перевода звонка `##NN`; основа —
юзерскрипт «Карта метро v8», координаты с лендинга SPOT, уточнения геокодером;
включая **Ветеранов 167к8**). Оснащение сверено с оператором 29.07.2026;
`boxes` — сколько боксов станция реально продаёт (число ссылок «Добавить» в
свободном слоте `/admin/record`), физическая конфигурация — в `layout`, и она
бывает больше. Новые
станции оригинала подхватываются автоматически (колонка появится без меты),
мету дописать одной строкой.

Как это видно на сайте: код `##NN` стоит рядом с названием станции везде
(карточки, шапка станции, боковой список, плашки на карте, поиск — код ищется
запросом с решётками); снежинка = заправка кондиционера; на карте счётчик
показывает **свободные** получасы и красится по их количеству
(зелёный / жёлтый ≤5 / красный — мест нет).

**Env бэкенда:** `ZMS_ADMIN_BASE_URL` (default `https://zamena-masla-spot.ru`),
`ZMS_ADMIN_LOGIN_PATH|LOGIN_FIELD|PASSWORD_FIELD` (если форма логина не
распознаётся сама), `ZMS_ADMIN_FETCH_TIMEOUT_MS`, `RECORDS_SYNC_INTERVAL_MS`.

**Разработка без боевой админки:** `node backend/scripts/zms-mock.js` (порт
3999, логин `admin`/`spot123`) + `ZMS_ADMIN_BASE_URL=http://127.0.0.1:3999` у
бэкенда. У мока есть `POST /__mock/down {"down":true}` — эмуляция падения для
проверки очереди — и `GET /__mock/records` — дамп записей.

## Quick start (Docker)

```bash
docker compose up --build

# Frontend → http://localhost:5173
# Backend  → http://localhost:3001
# Postgres → localhost:5432
```

Postgres-контейнер прогоняет миграции из `db/migrations/` при первом старте.
Без `TELEGRAM_BOT_TOKEN`/`SUPABASE_*` (не заданы по умолчанию в
`docker-compose.yml`) регистрация продолжает работать — заявки просто копятся
в БД без уведомления, а загрузка аватарки вернёт понятную ошибку.

## Backend setup (manual)

```bash
cd backend
cp .env.example .env          # fill DATABASE_URL, API_KEY, CORS_ORIGINS
npm install
npm run dev
```

| Env var | Description |
|---------|-------------|
| `DATABASE_URL` | PostgreSQL URI |
| `API_KEY` | Shared secret — must match `x-api-key` in all clients |
| `CORS_ORIGINS` | Comma-separated allowed origins |
| `PORT` | Default `3001` |
| `TELEGRAM_BOT_TOKEN` | Telegram bot token (@BotFather). Empty = bot disabled, registration requests just pile up unactioned |
| `ADMIN_TELEGRAM_ID` | Telegram user id seeded as the first bot admin (default `691442300`) |
| `SUPABASE_URL` | Supabase project URL — needed for avatar uploads to Storage |
| `SUPABASE_SERVICE_KEY` | Supabase **service_role** key (not anon) — write access to the `avatars` bucket |

Тестовые данные и проверка поиска:


### Вкладки сайта

Всё приложение — один ряд вкладок сверху (`.app-tabs` в `index.html`), каждой
соответствует свой хеш-роут:

| Вкладка | Роут | Что внутри |
|---------|------|------------|
| Профиль | `#/profile` (чужой — `#/user/:id`) | аватар, ник, статистика, лента активности, ачивки |
| Калькулятор | `#/` и `#/car/:id` | поиск по базе и страница машины |
| Записи | `#/records` | клон админки ZMS (ленивый чанк + Leaflet) |
| Скрипты | `#/scripts` | фид юзерскриптов для Tampermonkey |
| Что нового? | `#/news` | посты об изменениях сайта (`src/newsData.js`) |
| Топ | `#/top` | рейтинг по добавленным/отредактированным машинам |

Переключение вкладок **не сбрасывает работу**: страницы не пересобираются, а
прячутся. Набранный поиск и его выдача, открытая машина с выбранными агрегатами
и промывкой, выбранный день и открытая станция в записях, позиция прокрутки —
всё возвращается как было. Каждая вкладка помнит свой последний роут
(`lastRoute` в `main.js`), а раздел записей при уходе замирает (`pauseRecords()`)
и оживает при возврате (`resumeRecords()`) — фоновых опросов вне вкладки нет.
При выходе из аккаунта сохранённое состояние вкладок сбрасывается.

### Вкладка «Что нового?»

Лента постов об изменениях сайта. Единственное место правки — массив
`NEWS_POSTS` в `frontend/src/newsData.js`: новый пост добавляется объектом
**в начало** массива (`id`, `date`, `tag`, `title`, `lead`, `sections`).
`id` менять нельзя — по нему запоминается, что пост прочитан.

* Текст постов — для пользователей, а не для разработчиков: без терминов,
  путей и кода. **Эмодзи не используются** — оформление только inline SVG
  (иконки разделов задаются полем `icon`, набор — `ICONS` в `newsFeed.js`).
* Непрочитанное. Прочитанные посты лежат списком id в `localStorage`
  (`news_seen_post_ids`) — не «датой последнего визита»: посты можно править и
  переставлять, а список id от этого не врёт. На вкладке горит счётчик
  непрочитанного, он гаснет в момент захода на вкладку; плашка «новое» у самих
  постов остаётся до ухода со вкладки, иначе непонятно, что именно было новым.
* Дев-песочница: `npx vite` → `/dev-news.html` (кнопки гоняют состояние
  «прочитано / не прочитано» и счётчик).

### Учётка CRM привязана к аккаунту сайта

Панель «Наличие на станции» на странице машины спрашивает логин и пароль CRM
**один раз**: пара запоминается за пользователем (`crm_links`, пароль
зашифрован AES-256-GCM ключом `CRM_LINK_SECRET`), и дальше сессия CRM
поднимается сама — при входе на сайт (`warmCrmSession()` в `main.js`) и при
любом запросе к CRM, если сессию закрыли извне. Пароль в CRM сменили —
автовход получает `crm_auth_failed`, привязка стирается, панель просит войти
заново. Нет `CRM_LINK_SECRET` — пароли не запоминаются вовсе, панель работает
как раньше (вход руками каждый раз).

**А вот станция не запоминается — и это намеренно.** Панель открывается на
«выбери станцию…» при каждом заходе на машину. Раньше выбранный адрес лежал в
`localStorage` и панель на открытии карточки сама шла в CRM за фильтрами и
маслом — вхолостую: карточку часто открывают просто посмотреть, а работник в
этот день может стоять на другой станции, где и цены, и остатки другие. Запрос
к CRM уходит только после того, как адрес выбрали руками; дальше в пределах
открытой машины всё как было — смена вязкости чипами пробега перепроверяет
наличие сама.

Выход доведён до конца и по порядку: `POST /api/crm/logout` закрывает сессию
**в самой CRM** и проверяет это отдельным запросом, и только на успешном ответе
сайт гасит свою сессию (`frontend/src/profile.js`). Не подтвердилось —
из аккаунта не выходим, показываем ошибку и предлагаем повторить (и отдельную
кнопку «Всё равно выйти», если CRM недоступна надолго). Кнопка «Выйти» в самой
панели делает то же плюс снимает привязку (`unlink: true`).

**Выход закрывает всё и везде.** `POST /api/auth/logout` сносит ВСЕ сессии
пользователя (`destroyAllUserSessions`), а не только текущий токен: люди
работают в двух браузерах, и оставшийся залогиненным второй браузер первым же
запросом поднял бы сессию CRM заново по привязке — выход из CRM оказался бы
фикцией. Заодно на время выхода выключается автовход
(`crm/autoLoginPause.js`): между «CRM подтвердила закрытие» и «сессии сайта
снесены» есть щель, и в неё как раз успел бы влезть чужой браузер. Пауза
персональная, снимается явным действием человека (вход на сайт или вход в CRM
руками) и сама истекает через 5 минут. Побочный эффект, о котором надо знать:
сессия юзерскрипта — та же сессия сайта, так что выход на сайте разлогинит и
Tampermonkey-калькулятор.

> CRM завершает сессию аккаунта везде. Если под одной учёткой CRM работают
> несколько человек, выход одного завершит сессию и у остальных — раньше
> сессию намеренно не закрывали именно поэтому.
>
> Дев-песочница панели: `npx vite` → `/dev-crm-panel.html?state=linked`
> (`fresh`, `rejected`, `&logout=fail`) — фейковый бэкенд, без CRM.

**Сертификат CRM — отдельный вид отказа.** CRM живёт на своём сервере, и её
сертификат бывает просроченным или самоподписанным. Браузер работника такое
пускает после «всё равно перейти», а Node — нет: соединение рвётся, и панель
показывает «CRM недоступна». Текст ошибки специально говорит, что это
сертификат самой CRM и чинить его не на сайте, — раньше туда попадало голое
`CERT_HAS_EXPIRED: certificate has expired`, из которого не понять даже, у кого
сломалось. Пока сертификат чинят, соединение можно разрешить точечно, только
для CRM: `CRM_TLS_FINGERPRINT` (отпечаток печатает
`node backend/scripts/crm-tls-info.js`), `CRM_TLS_CA_FILE`, в крайнем случае
`CRM_TLS_INSECURE=1` — всё в `backend/src/http/tlsTrust.js` и `DEPLOY-VPS.md`.
Глобального `NODE_TLS_REJECT_UNAUTHORIZED=0` здесь быть не должно: тем же
процессом ходят телеграм, админка записей и каталоги.

### Мобильная версия

Телефон здесь — не «узкий десктоп», а самое слабое железо, на котором сайт
работает. Что из этого следует и почему:

* **Снимок базы не пересобирается зря.** Поиск и режим «Теги» работают поверх
  снимка всей базы (`GET /api/cars/index`, ~13к машин), а воркер держит по нему
  предпосчитанные триграммы. Собрать этот снимок заново — пик памяти на десятки
  мегабайт, и мобильная вкладка на таком пике выгружается: со стороны это
  выглядит как «сайт сам перезагрузился» с boot-экраном посреди работы. Поэтому
  свежесть проверяется версией (`?known=…`), при совпадении не качается и не
  пересчитывается ничего, а фоновое обновление не запускается, пока человек
  печатает в строке поиска (`loadSnapshot` в `main.js`).
* **Скоринг компактный.** `prepareCars` (`shared/carSearch.js`) держит триграммы
  не множествами строк на каждую машину, а одним словарём на снимок плюс
  `Uint32Array` из id — на реальной базе это 13 МБ вместо 46 и заметно быстрее.
  Выдача при этом бит-в-бит прежняя, это зафиксировано тестами
  (`carSearch.prepared.test.js`).
* **Сфера знает меру.** На тач-экранах у неё вдвое меньше узлов, ~30 кадров в
  секунду, буфер канваса не крупнее 2× и обрезанные подписи; цикл кадров
  полностью останавливается, когда страница поиска скрыта или вкладка ушла в
  фон (`sphere.js`). До этого главная занимала главный поток практически
  целиком, даже когда на неё просто смотрели.
* **Фоновые опросы спят вместе с браузером.** Записи и ачивки не ходят в сеть,
  пока `document.hidden` — возврат к странице догоняет всё разом.
* **Поля ввода — 16px на тач-экранах.** Меньше — и iOS Safari зумит страницу при
  фокусе, обратно не отматывая. Плюс `overscroll-behavior-y: contain` на
  документе: иначе «потянуть вниз» у верхней кромки перезагружает страницу в
  Chrome на Android.

### Темы оформления

Тёмная (по умолчанию) и светлая, кнопка-переключатель — справа в ряду вкладок и
в углу экрана входа. Выбор лежит в `localStorage` под ключом `cars_db_theme`.

Как это устроено:

* **Без мигания.** Тему ставит короткий синхронный скрипт в `<head>`
  (`index.html`) — до загрузки CSS и до первого кадра. Внешний модуль сюда не
  годится: он выполнится уже после отрисовки, и светлая тема успеет мигнуть
  тёмной. `src/theme.js` только переключает тему в работающем приложении.
* **Все цвета — токены.** `:root` в `style.css` держит тёмный набор,
  `:root[data-theme="light"]` — светлый. Прямых цветов в правилах нет: любой
  зашитый `#hex` пережил бы переключение и остался бы тёмным пятном.
* **Палитра, а не инверсия.** Жёлто-золотой акцент (L≈0.80) на белом даёт
  контраст ~1.5:1 и не читается, поэтому в светлой теме он уходит в глубокую
  бронзу (L≈0.52, ~5.7:1 к белому). Так же опущены зелёный/синий/красный и
  цвета спек-чипов; текст на сплошном акценте становится белым. Все смысловые
  пары проходят WCAG AA в обеих темах.
* **Не-CSS части.** Канвас-сфера на экране поиска (`sphere.js`) и тайлы карты
  станций (`records/map.js`, CARTO `dark_all` ↔ `light_all`) слушают событие
  `themechange` и перекрашиваются на лету, без перезагрузки.
* Boot-экран тоже светлеет: он показывается первым, и «чёрный экран → белый
  сайт» бил бы по глазам ровно так, как тема и должна была исправить.

   ```js

   const DB_API_KEY  = 'your-api-key';
   const DB_SITE_URL = 'https://cars.example.com';
   ```
2. В `userscript/src/oil-calculator/header.txt` добавить хост backend'а

3. Пересобрать: `npm run build:userscript` (или запушить — Action соберёт сам).

Кнопка открывает окно со всеми данными машины (объёмы, допуски, фильтры),

«этому роботу расчёт не делаем») и заметкой — всё можно поправить перед
отправкой. Повторная отправка той же машины обновляет запись, а не плодит дубли.

При нажатии «Отправить» юзерскрипт проверяет сохранённый токен сессии
(`GM_setValue`); если его нет или сервер ответил 401 (протух — например,
наступила полночь по МСК) — всплывает окно логина тем же аккаунтом, что и на
сайте. `created_by` в базе всегда берётся из этой сессии, а не из юзерскрипта.

**Нотификатор для коллег** (`SPOT DB Notifier-1.0.user.js`) — для тех, кто
работает по старинке и калькулятором не пользуется:

1. Установить Tampermonkey и скрипт по raw-ссылке.
2. Константы `API_BASE` / `API_KEY` / `SITE_URL` — в
   `userscript/src/notifier/app.js`, хост в `@connect` — в его `header.txt`.

Скрипт молча сидит на Mann Filter / LYNXauto; если найденная машина уже есть
в базе — показывает баннер «✓ эта машина уже рассчитана», клик открывает
страницу машины на сайте со всеми объёмами, допусками и ценами.

Ставить вместе с основным калькулятором не нужно.

## API reference

All endpoints require `x-api-key: <API_KEY>` header. Everything except
`/api/auth/login` and `/api/auth/register` additionally requires
`Authorization: Bearer <session token>` (see [Аутентификация](#аутентификация)
below) — sessions expire for everyone at midnight Moscow time.

| Method   | Path | Description |
|----------|------|-------------|
| `GET`    | `/health` | Liveness (no auth at all) |
| `POST`   | `/api/auth/register` | Registration request → pending, notified in Telegram |
| `POST`   | `/api/auth/login` | `{login, password}` → `{token, user}` |
| `POST`   | `/api/auth/logout` | Destroys **all** sessions of that user (logout everywhere) |
| `GET`    | `/api/auth/me` | Current session's user |
| `POST`   | `/api/cars` | Create/upsert car record (`created_by` = session user) |
| `GET`    | `/api/cars/match?engine_code=&brand=&model=&year=&volume=` | Best match |
| `GET`    | `/api/cars/search?q=` | Free-text search (top 20) |
| `GET`    | `/api/cars/:id` | Full record |
| `GET`    | `/api/cars?page=&limit=` | Paginated list |
| `GET`    | `/api/cars/index?known=<version>` | Compact snapshot of the whole base for client-side search/tags. `version` = `count:max(updated_at)`; passing a matching `known` returns `{version, unchanged:true}` without the cars |
| `PATCH`  | `/api/cars/:id` | Edit record (`comment` field → car_events) |
| `DELETE` | `/api/cars/:id` | **mod/admin only** — permanent delete |
| `GET`    | `/api/cars/:id/events` | This car's event feed (added/edited placards) |
| `PATCH`  | `/api/profile` | Change own display name |
| `POST`   | `/api/profile/avatar` | Upload avatar (multipart, `avatar` field) → Supabase Storage |
| `GET`    | `/api/profile/stats` | `{added, edited}` counts for the current user |
| `GET`    | `/api/profile/achievements` | Empty extensible placeholder feed |
| `GET`    | `/api/top` | Top users ranked by (cars added + cars edited); `{rows, excluded}` |
| `GET`    | `/api/crm/status` | CRM session state; signs in via the stored link if needed |
| `POST`   | `/api/crm/login` | `{login, password, remember?}` → CRM login, links the account |
| `POST`   | `/api/crm/logout` | Closes the CRM session (verified) — `{unlink}` also drops the link |
| `GET`    | `/api/crm/stations` | Station list parsed from CRM `/analyse/free` |
| `POST`   | `/api/crm/availability` | `{stationId, items}` → per-item CRM stock rows |

### Аутентификация

Two layers, stacked: `x-api-key` is a blunt "are you one of our clients"
gate (same as before); a session token on top identifies *which* user is
acting, drives `created_by`/`car_events`, and gates role-restricted actions
(`DELETE /api/cars/:id`). Registration is request-based: the form creates a
`registration_requests` row and pings admins in Telegram with Accept/Decline
buttons (request dies after 30 minutes). All sessions — for every user —
become invalid at the first minute of a new day in Moscow time
(`backend/src/auth/midnightMsk.js`), forcing a fresh login daily on both the
site and the userscript.

`POST /api/auth/logout` is a **global** logout: it destroys every session of
that user, not just the token that called it (see the CRM section above for
why). Other browsers and the userscript get a 401 on their next request and
fall back to the login gate.

### Telegram-админка

Бот отвечает только тем Telegram-аккаунтам, что есть в таблице `bot_admins`
(сидируется `ADMIN_TELEGRAM_ID` при первом старте). Команды в чате с ботом:

| Команда | Действие |
|---------|----------|
| `/users <текст>` | Поиск по имени/логину, у каждого — «Забанить», «Поменять ник», «Сделать модератором / Снять» |
| `/cars <текст>` | Поиск машин, у каждой — «Удалить машину» (с подтверждением) |
| `/addadmin <telegram_id>` | Передать доступ к этой админке ещё одному Telegram-аккаунту |

Заявки на регистрацию приходят отдельными сообщениями с кнопками
**✅ Accept / ❌ Decline** сразу при отправке формы на сайте — их не нужно
искать командой.
