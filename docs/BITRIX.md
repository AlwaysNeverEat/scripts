# Битрикс24: разбор протокола (без REST)

У компании облачный портал `spotexpress.bitrix24.ru` на дешёвой подписке, где
лимит REST-методов давно выбран, а прав на создание вебхука или локального
приложения у нас нет. Есть только логин и пароль обычного сотрудника.

Поэтому ходим тем же путём, что и браузер оператора: **служебными ajax-запросами
самого интерфейса**. Разметку страниц (десятки тысяч строк) при этом парсить не
нужно почти нигде — интерфейс общается с сервером JSON'ом и формами, а лимит
подписки на эти запросы не распространяется: браузер оператора и так дёргает их
сотнями за смену.

Всё ниже снято из DevTools живого сеанса (лид 611134, ноябрь 2025) и
проверяется только опытом: официального описания у этих ручек нет и меняться они
могут с любым обновлением портала. Отсюда правило: **любой разбор ответа
оборачиваем в try/catch и считаем, что формат мог поехать**.

## Общее у всех запросов

| Что | Значение |
|---|---|
| База | `https://spotexpress.bitrix24.ru` |
| Заголовок | `Bx-ajax: true` — без него отдаётся страница целиком, а не JSON |
| CSRF | `sessid` — в query, в теле формы и заголовком `X-Bitrix-Csrf-Token` |
| Куки | `PHPSESSID`, `BITRIX_SM_kernel*`, `BITRIX_SM_UIDH`, `BITRIX_SM_DTOKEN` |

`sessid` — это CSRF-токен, а не сессия: без кук он бесполезен. Берётся из
разметки любой страницы портала (`bx_sessid`) и живёт, пока жива сессия.

**Куку `BITRIX_SM_kernel_0` портал переписывает почти на каждый ответ.** Это не
шум: jar обязан обновляться после КАЖДОГО запроса, иначе через несколько
обращений сессия отвалится. Для сравнения, старая CRM (`backend/src/crm/`)
выдаёт куку один раз, и там это сходило с рук.

## Вход

Портал облачный, поэтому свой формы логина у него нет — он перекидывает на
Bitrix24.Network:

```
GET https://spotexpress.bitrix24.ru/online/
 → https://auth2.bitrix24.net/oauth/authorize/?client_id=…&redirect_uri=…&state=…
```

Сама форма — Vue-приложение, и вход идёт двумя ajax-шагами на
`auth2.bitrix24.net/bitrix/services/main/ajax.php`:

1. `action=b24network.authorize.verifyLogin` — есть ли такой аккаунт и каким
   способом его пускать;
2. `action=b24network.authorize.check` — проверка пароля; в ответе — возврат на
   `redirect_uri` с кодом, по которому портал и выдаёт свои куки.

Логин — почта (в куках видно как `BITRIX_SM_UIDL`).

Два места, где это ломается, и оба надо обрабатывать, а не «надеяться»:

- **капча** (`captchaSettings.isEnabled`, ошибка `ERROR_CAPTCHA`) — включается
  после нескольких неудачных попыток. Отсюда обязательная пауза автовхода при
  первой же неудаче, как в `crm/autoLoginPause.js`: иначе сайт продолжит
  долбиться устаревшим паролем, поймает капчу и убьёт вход для всех, включая
  человека с браузером;
- **подтверждение по телефону** (`b24network.phoneauth.confirm`). Если у
  аккаунта включена двухфакторка, серверный вход невозможен в принципе — тут
  нужен другой способ доставки сессии, а не доработка клиента.

## Ручки, которые нам нужны

### Сохранение лида — одно и на всё

```
POST /bitrix/components/bitrix/crm.lead.details/ajax.php?sessid=<sessid>
Content-Type: multipart/form-data
```

Ключевые поля тела:

| Поле | Пример | Смысл |
|---|---|---|
| `ACTION` | `SAVE` | |
| `ACTION_ENTITY_TYPE` | `L` | лид |
| `ACTION_ENTITY_ID` | `611134` | id лида |
| `EDITOR_CONFIG_ID` | `lead_details` | какая форма редактора |
| `STATUS_ID` | `IN_PROCESS` | **стадия** |
| `NAME` / `LAST_NAME` / `SECOND_NAME` | `Владимир` | имя клиента |
| `ASSIGNED_BY_ID` | `2182` | ответственный (id сотрудника) |
| `COMMENTS` | `[p]…[/p]` | описание, **BB-код**, не HTML |
| `TITLE` | `7 911 252-77-16 - Входящий звонок` | заголовок лида |
| `PHONE[698360][VALUE]` | `79112527716` | телефон |
| `ENABLE_REQUIRED_USER_FIELD_CHECK` | `Y` | проверка обязательных полей |

Из этого следуют три вещи, каждая из которых уже была бы багом.

**Все четыре нужных поля закрываются ОДНИМ запросом.** Стадию интерфейс двигает
отдельной ручкой (см. ниже), но `SAVE` принимает `STATUS_ID` наравне с
остальным. Двух запросов вместо одного не надо — а надо бы, они ещё и спорили бы
между собой.

**Редактор шлёт форму ЦЕЛИКОМ, а не изменённые поля.** Поэтому перед
сохранением обязательно читаем текущие значения: отправив форму без `TITLE` или
без телефона, мы их сотрём. В снятом сеансе это видно наглядно — стадию
переключили на `CANNOT_CONTACT` отдельной ручкой, а ушедший следом `SAVE` нёс в
себе `STATUS_ID=IN_PROCESS`, то есть копию из редактора.

**У телефона в имени поля стоит id существующего значения** — `PHONE[698360]`.
Так Битрикс отличает правку от добавления: `PHONE[n0]` завёл бы клиенту ВТОРОЙ
номер. Тот же порядок у `EMAIL`, `WEB`, `IM`.

### Смена стадии отдельно (не нужна, но пусть будет)

```
POST /bitrix/components/bitrix/crm.lead.list/list.ajax.php?sessid=<sessid>
ID=611134&ACTION=SAVE_PROGRESS&VALUE=CANNOT_CONTACT&TYPE=LEAD&EVENT_ID=<произвольный>&sessid=<sessid>
```

`EVENT_ID` — случайная строка от клиента, к серверу отношения не имеет.

### Список сотрудников для «ответственного»

```
POST /bitrix/services/main/ajax.php?context=CRM_ENTITY_EDITOR_USER&action=ui.entityselector.load
Content-Type: application/json
```

Отдаёт сотрудников с id, именем и аватаркой. Список меняется раз в полгода,
поэтому кэшируем его надолго, а не дёргаем на каждое открытие карточки.
Соседняя `ui.entityselector.saveRecentItems` — «недавно выбранные» в интерфейсе,
нам не нужна.

### Чего НЕ трогаем

- `/bitrix/tools/uf.php` — пользовательские поля (`UF_CRM_ROISTAT`,
  `UF_CRM_DCT_*` от Roistat). Описание лида живёт в СТАНДАРТНОМ поле `COMMENTS`,
  так что этот здоровенный запрос с подписями полей нам не нужен вовсе;
- `/_analytics/?st[...]` — телеметрия Битрикса;
- `canChangeCurrency`, `loadext`, `recentlyused.getlist`, `GET_FORMATTED_SUM` —
  обвязка интерфейса.

## Чего ещё нет в разборе

**Чтение лида.** Открытие карточки — это обычная навигация на
`/crm/lead/details/<id>/`, содержательных ajax-запросов при ней нет. Значит,
текущие значения полей берём либо из самой страницы (внутри неё лежит
JSON-конфиг редактора — разбирать надо его, а не разметку), либо из списка
лидов. Пока не снято.

**Поиск лида по входящему звонку.** Искать по номеру нельзя — это как раз то,
что упирается в лимиты. Вместо этого читаем список последних лидов: Манго
создаёт лид с телефоном в `TITLE` («7 911 252-77-16 - Входящий звонок») и
номером линии в `SOURCE_DESCRIPTION`, поэтому свежий звонок опознаётся без
всякого поиска.

## Карточка звонка: лид приезжает сам, искать не надо

Телефония у компании — Манго, и подключена она НЕ вебхуками, а полноценным
приложением Битрикса (`bitrix24.mango-office.ru`), которое живёт в размещении
`CALL_CARD`. Пока идёт разговор, страница портала держит для него форму, а в
ней — всё, что нам нужно про звонок:

```json
{
  "CALL_ID": "externalCall.02cd3f78….1787330828",
  "PHONE_NUMBER": "79112527716",
  "LINE_NUMBER": "78126034480",
  "CRM_ENTITY_TYPE": "LEAD",
  "CRM_ENTITY_ID": "611134",
  "CRM_BINDINGS": [{ "ENTITY_TYPE": "LEAD", "ENTITY_ID": "611134" }],
  "CALL_DIRECTION": "incoming",
  "CALL_STATE": "connected"
}
```

**Это снимает главный вопрос всей затеи** — как во время звонка узнать, какой
лид открывать. Никакого поиска по номеру (упирающегося в лимиты) и никакого
чтения списка последних лидов не нужно: связка «звонок → лид» уже посчитана
Битриксом и лежит готовой. Читать её надо оттуда же, откуда её берёт интерфейс,
— из канала обновлений портала (pull), а не из сохранённой страницы.

## Про REST: он на портале ЖИВОЙ

Рядом с теми же данными звонка лежит OAuth-токен приложения Манго:

```
AUTH_ID / REFRESH_ID / AUTH_EXPIRES=3600
SERVER_ENDPOINT=https://oauth.bitrix24.tech/rest/
APPLICATION_SCOPE=crm,placement,disk,messageservice,telephony,im,user_basic
```

То есть модуль REST на портале включён и права `crm` у приложений есть — вопрос
только в исчерпанном лимите ЗАПРОСОВ, а не в отсутствии самого API. Проверяется
это одним запросом (`crm.lead.get`), и проверить стоит: если лимит окажется не
мёртвым наглухо, вся возня с формами редактора отменяется.

Строить интеграцию НА ЭТОМ токене всё равно нельзя, и дело не в лимитах: он
выдан чужому приложению. Переустановят Манго, сменят подписку, отвалится их
сервер — и наш сайт встанет по причине, к нам отношения не имеющей. Как разведка
(«жив ли REST») — годится, как фундамент — нет.

## Осторожно при снятии страницы лида

Карточка лида открывается СЛАЙДЕРОМ поверх текущей страницы
(`?IFRAME=Y&IFRAME_TYPE=SIDE_SLIDER`), поэтому «сохранить страницу» из браузера
кладёт на диск не её, а то, что было под слайдером (обычно `/online/` — чат).
Карточку надо открывать отдельной вкладкой по прямому адресу
`/crm/lead/details/<id>/`.

## Композитный кэш: почему страницу нельзя просто скачать

Обычный `GET /crm/lead/details/<id>/` возвращает **общий для всех каркас
страницы**: ни имени клиента, ни стадии, ни телефона, ни даже `sessid`. У
портала включён композитный кэш (`frameCacheVars` с `"CACHE_MODE":"HTMLCACHE"`),
и настоящее содержимое браузер дозапрашивает вторым запросом:

```
GET /crm/lead/details/611134/?bxrand=<время>
BX-ACTION-TYPE: get_dynamic
X-Bitrix-Composite: get_dynamic
BX-CACHE-MODE: HTMLCACHE
BX-CACHE-BLOCKS: <json блоков из frameCacheVars>
BX-REF: <откуда пришли>
```

В ответ — JSON с динамическими блоками, и вот в них лежит страница (у лида это
`page-area`, но привязываться к имени нельзя: имена генерируются шаблоном).

Практический вывод, важнее самого механизма: **пустой ответ тут выглядит не как
ошибка, а как «лид без полей»**. Сохранив такую форму, мы стёрли бы лид
целиком — редактор шлёт все поля разом. Поэтому чтение считается успешным
только если в собранной разметке нашёлся `sessid`.

Отсюда же берётся проверка живой сессии: каркас портал отдаёт кому угодно,
включая незалогиненных, и судить по нему о входе бессмысленно.

## Чтение лида: модель лежит в разметке готовой

Карточка открывается СЛАЙДЕРОМ, то есть отдельным документом
`/crm/lead/details/<id>/?IFRAME=Y&IFRAME_TYPE=SIDE_SLIDER`. Прямой адрес без
`IFRAME` портал сам переводит в слайдер (`?any=details%2F<id>%2F`), поэтому
«открыть карточку отдельной страницей» — не вариант, а вот запросить её
по адресу слайдера можно.

Хорошая новость: **композитного кэша на ней нет** (в отличие от списка лидов),
хватает одного запроса. Вторая: разметку разбирать не нужно вовсе — Битрикс сам
кладёт в страницу все значения одним куском, для своего редактора:

```js
var model = BX.Crm.EntityEditorModelFactory.create(1, "", {
    entityTypeId: 1, data: {"ID":"268402","TITLE":"…","NAME":"Давид", …}
});
```

В модели 143 поля, из них обратно в форму уходит два десятка — остальное
производное (`FULL_NAME`, `ASSIGNED_BY_NAME`, даты), Битрикс считает его сам.

Три вещи, которые видно только на живых данных:

- **множественные поля** (`PHONE`, `EMAIL`) приезжают с `ID`, `VALUE`,
  `VALUE_TYPE`, `VALUE_EXTRA.COUNTRY_CODE` и `VIEW_DATA` — последнее готовая
  разметка для показа, и слать её обратно нельзя;
- **пользовательские поля** — объекты `{ SIGNATURE, IS_EMPTY }` у пустых и со
  значением у заполненных, а не голые строки;
- в значениях попадаются кавычки и фигурные скобки (комментарии операторов со
  ссылками на каталоги), поэтому JSON вырезается по балансу скобок С УЧЁТОМ
  строк.

И главное правило разбора: он либо возвращает лид, либо падает. Пустая модель
означала бы пустую форму, а сохранение пустой формы стирает лид целиком.

## Карточки звонков КОПЯТСЯ, и состояние в них врёт

Самое неочевидное место всей затеи. Приложение телефонии добавляет на страницу
портала форму на каждый звонок — и **не убирает и не обновляет её потом**. К
концу смены их там десяток, и у ВСЕХ `CALL_STATE` остаётся `connected`, даже у
звонков двухчасовой давности:

```json
{"CALL_ID":"externalCall.a5d8….1787378570","PHONE_NUMBER":"79668581045","CRM_ENTITY_ID":"467416","CALL_STATE":"connected"}
{"CALL_ID":"externalCall.f5a8….1787379349","PHONE_NUMBER":"79522752183","CRM_ENTITY_ID":"611142","CALL_STATE":"connected"}
```

Разница между этими двумя — тринадцать минут, и первый разговор давно кончился.

Значит, «идёт ли звонок» по карточке не определить. Определяется по времени: оно
зашито в сам идентификатор — `externalCall.<хэш>.<время в секундах>`. Отбор
свежего живёт в `shared/bitrixCall.js` (там же тесты, потому что на вкладке
Битрикса отлаживать нечем).

Без этого отбора датчик при каждой перезагрузке страницы вываливал бы на сайт
все звонки смены разом — и оператор получал бы пачку уведомлений о разговорах,
которые закончились час назад.

## Вход: точные тела ступеней

Сняты с бандла самой формы (`logging-in-scenario`), а не угаданы:

```
b24network.authorize.verifyLogin   { login }
b24network.authorize.check         { login, password, remember: '1' | '0' }
```

Три вещи, каждая из которых стоила одной живой попытки:

- **свой CSRF-токен.** У Bitrix24.Network он собственный и лежит в разметке
  страницы входа; токен портала там не годится. Без него — `Invalid csrf token`;
- **ничего лишнего.** Параметры OAuth со страницы (`client_id`, `state` и
  прочее) добавлять НЕЛЬЗЯ — в ответ прилетает `Wrong request`. Портал, ради
  которого идёт вход, Network берёт из своей сессии;
- **обычная форма, не JSON.** Так шлёт сама форма входа.

Ошибка про токен или формат НЕ считается отказом авторизации: на автовходе это
стёрло бы привязку учётки, и за нашу ошибку в разборе расплатился бы работник,
которому пришлось бы вводить пароль заново.

### Возврат на портал

Ручка `check` адреса возврата не отдаёт. Он и не нужен: форма после успешной
проверки просто идёт **по тому же адресу OAuth**, на который портал отправил в
самом начале. К этому моменту у Bitrix24.Network уже есть сессия, поэтому
второй заход не спрашивает пароль, а возвращает на портал с кодом — и уже
портал выдаёт свои куки.
