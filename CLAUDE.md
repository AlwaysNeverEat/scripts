# Как устроен проект (для агентов и для себя через полгода)

Три части в одном репозитории:

- `backend/` — Express API + телеграм-бот в том же процессе;
- `frontend/` — Vite-сайт (записи, карточки машин, калькулятор, админка);
- `userscript/` — Tampermonkey-скрипты для CRM и калькулятора масла;
- `backend/scripts/import/` — конвейер сбора данных (Motul, ROLF, MANN, BIG).

## Прод — СВОЙ СЕРВЕР, а не Supabase и не Render

Актуальная инструкция — **`DEPLOY-VPS.md`**. Всё живёт на одной машине
(`/opt/k-spot`, пользователь `deploy`):

| Что | Где |
|---|---|
| PostgreSQL 17 | контейнер `postgres` (`deploy/docker-compose.prod.yml`), порт только на `127.0.0.1` |
| Backend | контейнер `backend`, слушает `127.0.0.1:3001` |
| Сайт | статика в `/var/www/k-spot`, собирается `deploy/build-site.sh` |
| TLS и раздача | системный nginx на хосте + certbot (`deploy/nginx.conf`) |
| Аватарки | том `avatars` (`AVATAR_DIR=/data/avatars`), не Storage |
| Секреты | `deploy/.env` (см. `deploy/env.example`) |

**`DEPLOY.md` описывает СТАРЫЙ путь** (Supabase + Render + GitHub Pages) и
оставлен как история. Не предлагай команды для SQL Editor Supabase, дашборда
Render, переменных `SUPABASE_*`/`VITE_API_BASE` на GitHub Pages — на этом
проекте их больше нет.

Каталог `deploy/` есть **не во всех ветках** — он появился в ветке переезда
(`claude/api-spot-boot-recording-issue-qqvzan`), с которой сервер и живёт.
Прежде чем советовать `git checkout <другая ветка>` на сервере — проверь, что
`deploy/` в ней есть, иначе рабочая копия останется без скриптов деплоя.

### Типовые операции на сервере

```bash
# обновить код и перезапустить бэкенд
cd /opt/k-spot && git pull
docker compose -f deploy/docker-compose.prod.yml up -d --build

# пересобрать сайт (бэкенд трогать не нужно)
bash deploy/build-site.sh

# применить миграцию
docker compose -f deploy/docker-compose.prod.yml exec -T postgres \
    psql -U carsdb -d carsdb -v ON_ERROR_STOP=1 < db/migrations/0XX_имя.sql

# psql руками
docker compose -f deploy/docker-compose.prod.yml exec postgres psql -U carsdb -d carsdb

# бэкап
bash deploy/backup-db.sh
```

Миграции при первом наливе базы применяет `deploy/_pgcopy.sh`; дальше новые
файлы `db/migrations/*.sql` накатываются руками командой выше. Автоматического
трекера версий нет — миграции пишутся идемпотентными
(`CREATE TABLE/INDEX IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`).

## Импорт данных

Запускается на сервере обёрткой (контейнер переживает закрытие ssh, репозиторий
монтируется внутрь, поэтому пересборка образа не нужна — достаточно `git pull`):

```bash
bash deploy/scrape.sh <имя-скрипта.js> [аргументы]
docker logs -f <имя-скрипта-без-.js>
```

Порядок этапов и назначение файлов — `backend/scripts/import/README-v2.md`.
Коротко: `scrape-motul-all.js` → `scrape-rolf.js` (допуски) → `import-cars.js`
→ `build-enrichment-workset.js` → `scrape-filters.js` (MANN) →
`scrape-big-filter.js` → `apply-enrichment.js`.

Все долгие скрейперы чекпоинтят результат после каждой машины/группы и
пропускают уже обработанное — прогон можно прерывать и продолжать. Ответы
каталогов кэшируются в `data/import/cache/`.

Файлы данных: `data/import/motul-cars.json` (машины Motul; `scrape-rolf.js`
без `--out` дописывает допуски **прямо в него**), `cars-enriched.json`,
`cars-workset.json`, `filters.json`. В git лежат только `.gz`-снимки.

## Пасхалки в поиске

В строке поиска на главной есть ОДНО слово-ключ — `игры` (и `games`). Набранное
целиком, оно не ищет машину, и поиск на нём молчит (ни выдачи, ни «ничего не
найдено» — иначе пасхалка перестаёт быть пасхалкой), а по Enter открывает меню
игр `frontend/src/games.js`: иконка и название, клик запускает игру.

Слово одно на все игры сознательно. Раньше их было по одному на игру, и к пятой
получился список, который надо помнить наизусть, — пасхалка, ради которой ведут
конспект, не работает. Новая игра добавляется строкой в `GAMES` (`games.js`) и
иконкой, а НЕ новым словом в поиске.

Модуль игры грузится по клику в меню, а не вместе с ним: тринадцать игр — это
тринадцать чанков со словарями, спрайтами, колодой, физикой и колодой карт, а у
DOOM ещё и с движком в wasm — он один тяжелее всего остального сайта.
Иконки лежат уменьшенными до 256px, исходники и скрипт пересборки — `design/game-icons/README.md`.
Ветка `blank` в `GAMES` — для игры, которая уже работает, а иконка ей ещё
рисуется: она показывает на плитке значки вёрсткой — пустое место читалось бы
как «меню сломалось». Этим путём прошли шесть игр подряд, сейчас по нему идёт
DOOM. В `blank` кладут типографские знаки, а где их нет (якорь, прицел, взрыв,
череп — в шрифтах это либо цветное эмодзи, либо ничего), туда кладут SVG из
`icons.js`: значок такой же участник сетки плитки, как символ.

Строка ЛЮБОГО топа открывает профиль — и месячного на вкладке «Топ», и мини-топа
внутри окна игры. Помечает строку и слушает клик одно место на весь сайт,
`frontend/src/topProfile.js`; окно игры при переходе закрывается (профиль —
обычная страница под ним), а недоигранная партия при этом не теряется: все игры
запоминают её при закрытии.

Первые две устроены одинаково: слово — чистая функция от (id аккаунта, дата
МСК), считает её `backend/src/daily.js`. Своё у каждого, меняется в 00:00 МСК,
**в базе не хранится ничего**, миграций нет. Загаданное слово клиенту не
уходит: браузер шлёт попытку, сервер возвращает раскраску или место. Прогресс
живёт в localStorage под id аккаунта.

Словари обеих игр посчитаны заранее (README в каталогах). Python и модели нужны
только для пересборки, на сервере их нет и быть не должно.

Сапёр к суткам не привязан: поле генерируется заново после каждой победы и
проигрыша, а результаты нигде не хранятся — ни в базе, ни в браузере. Раскладка
мин живёт в памяти процесса (перезапуск бэкенда обрывает начатые партии — это
нормально) и клиенту не отдаётся до конца партии. Зато партия переживает F5:
состояние спрашивается у сервера.

Тетрис, тройка и пасьянс устроены иначе первых трёх, и это осознанно. Партия
считается В БРАУЗЕРЕ, а не на сервере: сапёр — это десяток запросов за партию, а
тут до тридцати действий в секунду (тетрис), партия на время, где каскад надо
показать в том же кадре (тройка), и карта, которая едет за курсором (пасьянс).
Правила целиком в `shared/tetris.js`, `shared/troika.js` и
`shared/solitaire.js` — формы и вращение SRS у первого, тройки, специальные
фишки и время у второго, раздача и «что куда ложится» у третьего, — а окна
`frontend/src/tetris.js`, `troika.js` и `solitaire.js` только рисуют и слушают
ввод. На сервер уходит ОДИН запрос — результат в конце партии, и он проверяется
на правдоподобность (`isPlausibleRun` из того же файла): это защита от мусора, а
не от человека с открытой консолью, и большего мини-топ пасхалки не стоит.

Маджонг живёт по тем же правилам и по той же причине: игрок один, все 144 фишки
лежат лицом вверх с первой секунды, и прятать не от кого — партия целиком в
браузере, на сервер уходит время разобранного стола.

У маджонга есть одна вещь, которой нет ни у одной другой пасхалки, — РАЗДАЧА
ГАРАНТИРОВАННО РАЗБИРАЕМА. Случайно разложенная «черепаха» не разбирается
примерно в трети случаев, а топ по времени превратился бы в лотерею «кому
досталась хорошая раскладка». Поэтому стол собирается ЗАДОМ НАПЕРЁД: берутся два
места, свободных ОДНОВРЕМЕННО (не «первое, убрали, посчитали заново, второе» —
такой ход в настоящей партии сделать нельзя), в них кладётся пара, места
занимаются, и так 72 раза. Порядок сборки и есть готовое решение — на нём стоит
главный тест в `shared/mahjong.test.js`, он прогоняет решение ход за ходом теми
же `canTake`/`take`, которыми играет окно. Тупик после этого остаётся возможным,
но он теперь ЧЕЙ-ТО ВЫБОР, а не свойство раздачи; на этот случай есть кнопка
«Перемешать», и включается она ТОЛЬКО в тупике — перемешивают не «ещё разок», а
выход из положения, в которое игрок себя загнал сам. Перемешивание раскладывает
оставшиеся фишки тем же способом, то есть стол снова разбирается.

Подсказки по кнопке в маджонге нет и не будет: соревнуются временем, и кнопка
«покажи пару» превратила бы топ в соревнование по скорости нажатия на неё.
Вместо неё стол сам подсвечивает пару, если игрок восемь секунд не ходит (как в
тройке), а `findMove` возвращает на одном и том же столе всегда одну и ту же
пару — подсказка не должна прыгать.

Фишки маджонга — третья игровая графика проекта (после фишек тройки и карт
пасьянса): один спрайт `frontend/src/assets/mahjong-tiles.png` (сетка 7×6),
строка и столбец считаются прямо из `KINDS` в `shared/mahjong.js`, таблицы
соответствия нет нигде — **порядок `KINDS` менять нельзя, не пересобрав
спрайт**. Исходный лист и сборщик — `design/mahjong-tiles/README.md`. Главная
особенность вёрстки: у фишки нарисованы ЛИЦО И БОРТИК, и шаг сетки равен ЛИЦУ, а
не картинке, — соседняя фишка закрывает бортик собой, как в настоящей горке.

Бильярд стоит особняком у всех сразу, и причина одна: он ПАРНЫЙ. Очко, которое
игрок себе приписал, отнято у живого человека, поэтому грубой проверки «бывает ли
такой результат» тут не хватает — партию ВЕДЁТ СЕРВЕР (`backend/src/pool/`). Он
принимает удар (четыре целых числа: направление, сила и куда поставили биток),
применяет его своей копией правил и хранит получившуюся позицию.

Считается при этом партия всё равно в браузере — у обоих. Физика в `shared/pool.js`
сделана ДЕТЕРМИНИРОВАННОЙ: тот же удар из той же позиции даёт тот же результат в
любом браузере и на сервере, поэтому по сети едет удар, а не шестнадцать шаров, и
соперник видит, КАК они разъехались. Держится это на трёх вещах, ломать которые
нельзя: в ядре физики нет `sin/cos/atan2/hypot` (стандарт не фиксирует их до
последнего бита, и Firefox разошёлся бы с Chrome), вход целочисленный, а пары
шаров перебираются строго по номерам. После каждого удара окно сверяет отпечаток
позиции (`stateHash`) с серверным и при расхождении берёт серверную: молча играть
дальше нельзя — двое видели бы разные столы.

Живая игра вдвоём сделана ОПРОСОМ раз в полторы секунды, а не веб-сокетами: ходят
по очереди, действует один человек, задержки не видно, а сокеты потребовали бы
отдельной настройки nginx (`DEPLOY-VPS.md`) ради того, чего никто не заметит.

Бот (`shared/poolBot.js`) перебирает удары ТЕМ ЖЕ движком: берёт копию позиции,
бьёт и смотрит на результат. Знать больше игрока он поэтому не может. Сложность —
это дрожь руки (случайный угол), а не глупость: слабый бот выбирает тот же лучший
удар, просто хуже его исполняет. Партии с ботом живут только в браузере, сервер о
них не знает и в таблицу очков они не идут — иначе первое место занял бы не тот,
кто обыгрывает людей.

Стол семифутовый (78×39 дюймов), а не турнирный девятифутовый: шар к сукну
крупнее (на экране это разница между «видно номер» и «видно точку»), и партия
короче. Подкрутки, прыжков и заказа лузы нет сознательно — см. шапку
`shared/pool.js`.

У лузы ДВА размера, и путать их нельзя: `POCKET_R` — радиус захвата (шар падает,
когда его ЦЕНТР ближе этого), `POCKET_MOUTH` — вырез в борте, внутри которого
борта для шара нет. Второй ровно на радиус шара больше первого, и рисуется луза
именно по нему — тогда шар пропадает, когда целиком вошёл в неё. Если рисовать по
радиусу захвата и не делать выреза, лунка выглядит вдвое больше своей рабочей
области: шар в неё «влезает», отскакивает от борта поперёк устья и уезжает
обратно. Числа физики (трение, края шкалы силы, отскок борта) подобраны замерами
ДЛИНЫ ПУТИ шара, а не его конечной точки: он отражается от бортов и возвращается,
так что по конечной точке выходит ерунда.

Чужой удар показывается ЦЕЛИКОМ: сначала на столе появляется кий и линия прицела
соперника, потом замах, и только потом едут шары (`showAim` в
`frontend/src/pool.js`). Одинаково для бота и для человека — на вход тот же удар
из четырёх чисел. Без этого соперник выглядит невидимой силой, двигающей шары.

Сукно, борт и кий — КАРТИНКИ (`frontend/src/assets/pool-*.webp`), шары остаются
вёрсткой: цветной круг с номером читается на экране лучше фотографии шара
размером в двадцать пикселей. Лузы отдельной картинкой не рисуются — они
нарисованы в самом борте, и весь стол выравнивается одним действием: внутренний
прямоугольник картинки борта натягивается на игровое поле, после чего все шесть
луз сами встают в свои игровые точки. Отсюда же берутся толщина борта и размер
холста — руками они нигде не заданы. Раскладка исходного листа, замеры и команда
пересборки — `design/pool-table/README.md`.

Размер лузы В ФИЗИКЕ задан КАРТИНКОЙ, а не наоборот: `POCKET_MOUTH` равен
замеренной полуширине выреза средней лузы (3.83"), `POCKET_R` — на радиус шара
меньше. Перерисуют борт — эти числа надо пересчитать, иначе шары начнёт отбивать
от невидимого борта посреди нарисованной лунки.

Дурак отличается от ВСЕХ остальных пасхалок одним: в нём есть ЗАКРЫТАЯ
ИНФОРМАЦИЯ. Тетрис, тройка и пасьянс считаются в браузере целиком — там нечего
прятать. Бильярд считается в браузере у обоих, потому что стол виден обоим, и
сервер лишь сверяет отпечаток. В картах так нельзя: браузер, знающий чужую руку и
колоду, знает лишнее. Поэтому партию с людьми ВЕДЁТ СЕРВЕР, а каждому игроку
уезжает не позиция, а ЕГО ВИД на неё (`viewFor` в `shared/durak.js`): своя рука,
РАЗМЕРЫ чужих рук, стол, отбой и козырь. Сверок отпечатка, как в бильярде, тут
нет и быть не может — клиенту нечего пересчитывать.

Из этого же следует главное правило при правках: «что мне сейчас можно» считают
`attackCards`/`defendCards`/`transferCards`/`canTake`/`canPass`, и все пятеро
берут на вход ВИД, а не позицию. Тем же видом пользуется бот — поэтому он
физически не может подглядеть в чужие карты, а не «мы попросили его не
жульничать».

Движок с самого начала написан на 2–4 игроков и на оба режима, а не «на двоих,
потом расширим»: круг, добор и подкидывание в дураке устроены вокруг «следующего
по кругу», и вкручивать это в готовую игру на двоих означало бы переписать её
целиком. Партия один на один — это тот же код при `seats = 2`. Комнату собирают в
лобби (сколько мест и какие правила), полный стол начинает партию сам, а хозяин
может начать и неполным — тогда мест в партии столько, сколько людей реально
село.

Сложность бота — это ГЛУБИНА СЧЁТА, а не фора и не дрожь руки, как в бильярде:
Новичок кладёт козырную шестёрку вперёд некозырной десятки, Любитель знает цену
козырю, а Шулер вдобавок считает вышедшее (когда колода пуста и играют двое,
«что осталось у соперника» — это вычитание, а не догадка). Отсюда панель
«вышло» в окне: раз сильный бот считает отбой, прятать отбой от человека
нечестно — иначе бот знал бы больше, а не считал лучше. Все три уровня и пороги
подобраны турниром бот-против-бота (`shared/durakBot.test.js` его и стережёт):
Любитель обыгрывает Новичка примерно в трёх партиях из четырёх, Шулер Любителя —
чуть чаще половины, и это честно: счёт карт решает в концовке, а до неё оба
играют одинаково разумно. Числа в боте (брать ли вместо отбоя, подкидывать ли
всё подряд) не «на вкус»: и то, и другое проверялось тысячей партий, и оба раза
осторожный вариант ПРОИГРЫВАЛ.

Ход в дураке ПОКАЗЫВАЕТСЯ: карта летит из руки на стол, побитый розыгрыш уезжает
в отбой, раздача и добор рассыпаются из колоды по рукам, а «бито», «беру» и
«перевод» вдобавок пишутся крупно поверх стола. Без этого стол просто
подменяется — карта исчезает из руки и в тот же кадр лежит на столе, а розыгрыш
пропадает целиком; за столом на четверых понять, что произошло, невозможно.
Считается показ ИЗ РАЗНИЦЫ ДВУХ ВИДОВ (`diffViews` в `frontend/src/durak.js`), а
не из «какой ход мы сделали»: с ботом ход известен, а с людьми с сервера
приезжает позиция, и рассказа о ней там нет — разница же видов есть в обоих
случаях и означает одно и то же. Если разницу объяснить не вышло (вкладка спала,
сервер ушёл на несколько ходов вперёд), показ пропускается: три чужих хода подряд
всё равно смотреть некому.

Единственное неочевидное место в правилах — счётчик простоя (`STALL_BOUTS`). В
переводном двое с пустой колодой могут крутить карты вечно: защитник берёт, на
следующем розыгрыше переводит взятое обратно, второй берёт его же, в отбой не
уходит ничего. Это не теория — партия ботов так и зависла (200 000 ходов без
конца). Шестьдесят розыгрышей подряд без единой карты в отбое считаются ничьей,
как правило пятидесяти ходов в шахматах; честной игрой в этот потолок упереться
нельзя (у случайной, которая берёт куда чаще человека, самая длинная серия была
34).

Рогалик — карточный забег в духе Slay the Spire, и он ближе всего к тетрису с
тройкой: игрок ОДИН, соперника нет, закрытой чужой информации нет — прятать не от
кого, поэтому забег целиком считается В БРАУЗЕРЕ, а на сервер уходит один запрос
с результатом. Сравните с дураком: там сервер ведёт партию не «на всякий случай»,
а потому что браузер, знающий чужую руку, знает лишнее.

Устроен он двумя файлами, и граница между ними жёсткая: `shared/roguelike.js` —
ПРАВИЛА (бой, карта узлов, лут, эскалация), `shared/roguelikeContent.js` —
КОНТЕНТ (27 карт, 5 врагов, 2 босса, 9 модификаторов, 10 мутаций, 6 событий).
Движок не знает ни одной карты по имени: карта — это список эффектов
(«нанести 6 урона», «дать 5 блока», «наложить 3 яда»), и добавляется она строчкой
в контент, а не веткой в коде. Появившийся в правилах `if (card.id === ...)`
означает, что затея сломана.

Разнообразие берётся не из объёма написанного, а из ПЕРЕМНОЖЕНИЯ: пять базовых
врагов × девять модификаторов (ярость, шипы, вампиризм, ускоренный…) × номер
цикла дают сотни разных встреч. Уникальных боссов ровно два на всю игру — босс
отличается не именем, а здоровьем, двумя гарантированными модификаторами и тем,
на каком цикле его встретили. Полсотни нарисованных вручную врагов — это способ
выдохнуться на пятнадцатом.

Бесконечность у забега ДВУОСНАЯ, и обе оси нужны разом. Первая — циклы: пройден
босс, карта генерируется заново, у врагов +35% здоровья и +22% урона за каждый
пройденный цикл. Вторая — колода: точильный камень даёт +1 уровень КОНКРЕТНОМУ
экземпляру карты (два «Удара» качаются независимо), и уровень — это ровный
line-scaling, +30% к числам, одной формулой на весь контент. Без второй оси
забег упирается в арифметику эскалации, без первой — не кончается вовсе.

Ровная эскалация по циклам держится ровно до тех пор, пока так же ровно растёт
колода. Но колода растёт УМНОЖЕНИЕМ: уровень карты, чары с их ×2 → ×4 → ×8 и
легендарка вместе дают удар не на 30, а на 300 — и к четвёртому циклу забег
превращается в прогулку. Поэтому с `ADAPT_LOOP` (четвёртый цикл) враг считается
не только от номера цикла, но и ОТ ИГРОКА: правила помнят его урон за ход и
броню за ход (скользящее среднее по боям, а не один удачный ход), и подгоняют
здоровье врага так, чтобы бой длился положенные ходы, а удар — так, чтобы броня
не съедала его целиком.

Потолки подгонки РАЗНЫЕ по типу врага, и это главное: рядовой остаётся рядовым
(крыса с девятью тысячами здоровья — не сложность, а тоска), элита заметно
крепче, а стеной становится босс. Раньше четвёртого цикла подгонки нет вовсе:
первые циклы должны читаться как «я стал сильнее», а не как «игра догоняет».

Легендарок ровно ТРИ на всю игру, и живут они по своим правилам: обычным броском
редкости не выпадают вовсе (вес 0), а шанс считается отдельно (`legendChance`) и
растёт с циклом — в первом это почти случайность, к третьему легендарку видит
примерно каждый второй забег, к пятому — почти каждый. Каждая ВЫПАВШАЯ делит шанс
следующей на пять: две за забег — редкость, три — история. Занимает она одно из
трёх мест в награде, а не приходит вместо выбора, и второй копией не приходит
никогда. Карт три, потому что осей три, и спорить друг с другом им незачем:
ТЕМП («Сердце горна» — +1 энергия каждый ход), МНОЖИТЕЛЬ («Зеркальный зал» —
первая карта хода срабатывает дважды) и ВЗРЫВ («Час расплаты» — бьёт за каждую
сработавшую до него карту, то есть за собственное место на столе).

Из «одной формулы» следует, что уровень растит только ЧИСЛА (урон, блок,
лечение, статусы), а добор, энергию и удвоение — нет: «тянет 2.6 карты» не
число, а действие. Поэтому камень такие карты и НЕ БЕРЁТ (`canLevel`): молча
съесть камень у «Сосредоточения», которое на любом уровне тянет свои две карты,
— это обман, а не строгость правила. По той же причине их пропускает «Кузница».

Отдельно от уровня живут МУТАЦИИ карт: редкий осколок вешает на карту условный
эффект («×2 урона, если у врага нечётное здоровье», «первые N розыгрышей за бой
бесплатны»). Та же мутация повторно НЕ ложится второй строкой, а УМНОЖАЕТ
первую: ×2 → ×4 → ×8. Именно из-за этого удвоения осколки и падают так редко,
причём шанс растёт с циклом: ×8 на восьмом цикле — заслуженный финал забега, на
первом — сломанный баланс.

РАЗНЫХ мутаций на карте не больше четырёх (`MAX_MUTATIONS`): дальше осколок не
добавляет пятую строку, а усиливает одну из уже висящих. Потолок не про силу — с
тем же удвоением карта продолжает расти, — а про читаемость: карта с десятком
строк перестаёт быть картой, её нельзя ни показать, ни удержать в голове. По той
же причине на самой карточке уровень и чары — ДВЕ КОРОТКИЕ МЕТКИ и свечение
рамки (золотое за уровень, фиолетовое за чары), а что именно навешано,
рассказывает панель сбоку по наведению. Список поверх картинки к пятой мутации
вылезал за её край, и прочитать его там всё равно было нельзя.

Намерение врага ВИДНО ДО ХОДА ИГРОКА и показанными числами — с его силой,
ослаблением и множителем цикла; лежит оно РЯДОМ КАРТОЧЕК с подписью «использует
в следующем ходу», как рука напротив. Это не украшение: без него броня ставится
наугад, и вся сборка колоды теряет смысл. Поэтому и подписано намерение словами
(«Бьёт 12»), а не значком меча: половина шрифтов рисует его цветной картинкой, и
число рядом читается как что угодно.

БРОНЯ НЕ СГОРАЕТ и копится от хода к ходу — как в карточных играх с героем, а не
как в рогаликах с одноразовым блоком. Разница принципиальная: сгорающий блок
наказывает за «переставил лишнего», а броня превращает защиту во вложение.
Из-за этого числа защиты в контенте маленькие (защита за энергию заметно меньше
урона врага за ход): иначе выгодно закрыться наглухо и не бить вовсе, бой
перестанет кончаться, а забег превратится в соревнование по терпению — тот же
довод, по которому в тройке кончается время. Здоровье и броня показываются
ЧИСЛАМИ, а не полосами: весь расчёт хода тут в целых числах («бьёт 12, у меня 7
брони и 9 здоровья»), а полоса отвечает только на «много или мало».

Ход игрока — это ЗАЯВКА, а не череда немедленных действий. Карта, которую
вытянули из руки на стол, СРАЗУ стоит энергии, но не делает ничего: ни здоровье,
ни броня не двигаются, пока не нажат «Ход». Тогда стол срабатывает СЛЕВА
НАПРАВО, в порядке выкладывания, и только там видно, что вышло. Смысл в том, что
ход приходится считать в голове заранее — с ослаблением, уязвимостью и бронёй, —
а не подбирать по одной карте, глядя на уже уехавшее здоровье врага. Порядок
карт на столе поэтому тоже решение: «Зеркало» перед «Размахом», «Порча» перед
атаками, «Засада» первой.

Отменить выкладывание нельзя (энергия потрачена, добор уже случился), а вот
ПЕРЕСТАВИТЬ карты на столе — можно, перетаскиванием: перестановка ничего не
отменяет, а ошибиться в порядке легко, карты кладут быстро.

Из отложенного розыгрыша есть РОВНО ОДНО исключение, и оно не «для удобства»:
добор, энергия и улучшение карты в руке (INSTANT в `shared/roguelike.js`)
срабатывают при выкладывании. Они меняют не бой, а САМУ ЗАЯВКУ — что игрок ещё
успеет положить на стол; карта, которая тянет карты в конце хода, тянет их в
руку, уходящую в сброс, то есть не делает ничего. По той же причине карта с
`bounce` («Эхо-камень») возвращается в руку не сразу, а в начале следующего хода.

Карта, У КОТОРОЙ ВСЯ РАБОТА МГНОВЕННАЯ («Адреналин», «Сосредоточение»,
«Кузница»), на стол вообще не ложится — `isFlash` в правилах: она уже отработала
и на столе только загораживала бы карты, которые действительно сработают по
«Ходу». Вместо переезда на стол она вспыхивает на своём месте и уходит в сброс —
с подписью, ЧТО именно сделала («+2 карты»), а добранные карты приезжают в руку
по одной и уже после вспышки: иначе карта просто исчезает, а рука в тот же кадр
становится другой, и понять, что произошло, нельзя.
Чара с боевым эффектом («Оберег», «Отрава», «Пиявка») снимает карту со вспышек:
теперь ей есть что делать в бою, а значит, место на столе.

Улучшение показывается ОТДЕЛЬНО и заметно: «Кузница» выбирает карту в руке
случайно, поэтому окно пишет, кого именно улучшили, и зажигает саму карточку
с подписью «N уровень». Тихо выросший уровень в углу одной из пяти карт не
читается вовсе — а это единственное, что карта делает.

Ход ПОКАЗЫВАЕТСЯ, как в дураке, но проще: карта улетает из руки на стол (и это
честный FLIP — она уже нарисована на своём месте, а мы лишь отпускаем её из
руки), потом по «Ходу» стол загорается карта за картой, над врагом отлетают
цифры, счётчики едут, невыложенная рука уезжает в сброс, и только потом плашка
«Ход врага» и его удар в ответ. Держится это на ЖУРНАЛЕ (takeLog в правилах):
правила считают ход целиком и мгновенно, но пишут каждый шаг — какая карта
сработала (`cast`), сколько прилетело и сколько осталось здоровья и брони, — а
окно проигрывает журнал по событию и рисует счётчики из своей копии, а не из
состояния движка. Оттуда же копии стола, руки и намерения на время показа:
правила к этому моменту уже раздали новую руку и загадали врагу СЛЕДУЮЩЕЕ
намерение, а игрок смотрит на предыдущий ход. В дураке показ вычисляется
разницей двух видов, потому что позиция приезжает с сервера без рассказа о том,
что случилось; здесь правила и окно в одном браузере, и рассказать честнее.

Рука лежит ВЕЕРОМ внахлёст, и поднятую карту выбирает JS (ближайшую к курсору),
а не `:hover`. Причина простая: карты перекрывают друг друга, поднимаясь, карта
уезжает из-под курсора, курсор попадает на соседку — и веер дрожит. Раскладка
(шаг, разворот, размер карточки) считается в окне, потому что зависит и от числа
карт, и от размеров окна: бой обязан помещаться целиком, карту нельзя выложить,
если до руки надо доскроллить.

Перед боссом на карте всегда стоит костёр — один узел на строку, мимо не пройти.
Без него исход боя с боссом решала бы не колода, а то, сколько здоровья случайно
осталось за одиннадцать узлов до него; с ним на костре появляется решение
(отдохнуть или заточить карту).

Числа контента подобраны не на глаз: в `shared/roguelike.test.js` живёт
АВТОИГРОК — простой бот, играющий забег по тем же функциям, что и окно. Он
стережёт две границы: забег обязан заканчиваться (бесконечность — не вечность), а
первый цикл средний игрок должен проходить примерно в двух третях забегов и
никогда не доходить до десятого. Правка баланса «на глаз» ломает обе границы
молча.

Всё случайное идёт через ОДИН генератор с сидом (xorshift32 в правилах): ни
одного `Math.random` ни в правилах, ни в окне. Сид нужен не для красоты — по нему
воспроизводится жалоба «вот на этом забеге сломалось», на нём стоят тесты, и на
нём же однажды сделают забег дня, не переписывая игру.

Забег переживает не только закрытие окна, но и перезагрузку страницы: состояние —
обычный объект без функций, и оно целиком уезжает в localStorage под id аккаунта.
В отличие от тройки, где партия живёт минуты, забег идёт десятки минут, и терять
его от случайного F5 нельзя. Время при этом копится ТОЛЬКО пока окно открыто и
вкладка видима — иначе «полтора часа» в подписи рекорда означало бы «вкладка
висела с ночи».

Графика у рогалика подключается ПО ИМЕНИ ФАЙЛА: положили
`frontend/src/assets/roguelike/strike.png` — и «Удар» нарисован, кода править не
надо (`import.meta.glob` в окне игры). Никакой таблицы «карта → картинка» нет:
имя файла и есть id карты. Карты без файла рисуются вёрсткой — колода
дорисовывается неделями, и смешанная рука это переходное состояние, а не
поломка.

На картинке НЕ рисуются числа и описание: они меняются от уровня и мутаций
(«Удар» 4 уровня с ×4 бьёт совсем не на 7), а описание собирает движок из
эффектов. Шар с числом при этом бывает ТОЛЬКО У АТАКИ: он нарисован на рамке
оружия и означает урон, а блок, положенный на его место у умения, читается как
«столько эта карта бьёт». Что уже стоит в шаре, описание второй раз не пишет, а
длинный текст УМЕНЬШАЕТСЯ шрифтом, а не обрезается рамкой: обрезанная карта
перестаёт объяснять, что делает. Стоимость, главное число и текст кладутся
поверх текстуры в пустые поля рамки — шрифтом Bitter (`frontend/src/assets/fonts/`, SIL OFL): системный
гротеск сайта спорил бы с брусковой антиквой на самой рамке. Что рисовать, каких
размеров, какую рамку брать под атаку и умение и куда попадают числа —
`design/roguelike-cards/README.md`.

Морской бой — вторая после дурака игра с ЗАКРЫТОЙ ИНФОРМАЦИЕЙ, и в ней это
выражено сильнее всего: в картах закрыта чужая рука, здесь — чужая расстановка,
то есть игра целиком. Браузер, которому её отдали, не «может смухлевать» — он уже
выиграл. Поэтому партию с людьми ведёт СЕРВЕР (`backend/src/battleship/`), а
каждому уезжает его вид (`viewFor` в `shared/battleship.js`): свой флот, чужие
выстрелы по нему, свои выстрелы по чужому полю и ПОТОПЛЕННЫЕ чужие корабли. Живые
чужие не уезжают никогда — до конца партии, после которого открывается всё:
посмотреть, где стояли ненайденные, — половина удовольствия, а портить уже нечего.

Партия идёт в ДВА ЭТАПА, и расстановка — не окно настроек перед игрой, а часть
партии: соперник уже сидит, из расстановки можно сдаться, и её же забирают, если
человек ушёл, не расставившись. Расставляются оба ОДНОВРЕМЕННО (ждать чужой
расстановки незачем — она всё равно закрыта), и отсюда единственное место в
проекте, где двое пишут в одну строку базы разом. Обычная защита по `seq`, как у
выстрела, тут не годится: она объявила бы одного «опоздавшим» и заставила
расставлять флот заново. Вместо неё каждый пишет ТОЛЬКО СВОЙ КУСОК позиции
(`jsonb_set` по своему месту) с условием «этот игрок ещё не готов» внутри того же
UPDATE — потерять чужую расстановку, перезаписав её своей копией, невозможно.

Правила классические русские: поле 10×10, флот 4-3-3-2-2-2-1-1-1-1, корабли не
касаются даже углами, попал — стреляй ещё, вокруг потопленного вода отмечается
сама (расстреливать заведомо пустые клетки — это удлинять партию ничем). Залпового
режима, поля 12×12 и «кораблей буквой Г» нет сознательно: это домашние правила, о
которых за одним столом договариваются вслух, а в офисной пасхалке они дают только
споры «а у нас так не играют».

Сложность бота (`shared/battleshipBot.js`) — это ГЛУБИНА СЧЁТА, как в дураке, а не
дрожь руки, как в бильярде: Юнга бьёт наугад, Наводчик ищет по сетке и добивает
линией, Адмирал считает, сколько расстановок живых кораблей проходит через каждую
клетку. Всё, чем Адмирал отличается от человека, — он не забывает: и то, что
корабли не касаются бортами, и то, что потопленные обведены водой, и живые длины
человеку тоже написаны на панели. Расстановку бот делает случайную на ВСЕХ
уровнях, и это не лень: своё поле — единственное, чего соперник не видит совсем, а
любая осмысленная схема («по краям», «в углу») — это узор, который живой человек
запоминает с третьей партии.

Уровни стережёт `shared/battleshipBot.test.js`, и он меряет ДВА числа. В поиске
крупных кораблей разрыв большой (около 42 выстрелов у Адмирала против 55 у Юнги),
а в целой партии втрое меньше — и это свойство игры, а не недоделка бота: хвост
партии, четыре однопалубных, не ищется НИЧЕМ (все оставшиеся клетки для них
равновероятны), а умный бот ровно потому и оставляет себе больше непроверенных
клеток. Правка бота «на глаз» ломает обе границы молча.

Корабли на поле рисуются НЕ КЛЕТКАМИ, а полосами поверх сетки (четырёхпалубный из
четырёх подкрашенных клеток читается как четыре катера в ряд), а отметки выстрелов
лежат ещё выше: пока у клеток был свой непрозрачный фон, попадание в собственный
ещё не потопленный корабль пряталось под его корпусом — то есть игрок не видел
ровно того, что ему важнее всего. Все значки — SVG (`frontend/src/icons.js`), эмодзи
нет ни одного, и причина та же, что в сапёре: 💥 и 🌊 рисует операционная система,
в каждой по-своему, и подогнать их под клетку в двадцать шесть пикселей, под тему и
под подсветку последнего выстрела нельзя никак.

Шашки (русские) — вторая парная игра БЕЗ закрытой информации, после бильярда, и
это главное, что стоит про них помнить. В дураке и морском бое сервер отдаёт
игроку не позицию, а ЕГО ВИД на неё, потому что чужая рука и чужая расстановка
закрыты. В шашках закрытого нет ВООБЩЕ НИЧЕГО: доска на виду у обоих с первого
хода. Поэтому `viewFor` в `shared/checkers.js` нет вовсе, и городить его ради
симметрии значило бы делать вид, что тут есть тайна.

Партию всё равно ведёт СЕРВЕР (`backend/src/checkers/`), но по другой причине —
по бильярдной: игра парная, и очко, которое игрок себе приписал, отнято у живого
человека. Только бильярду сервер нужен как арбитр над физикой, а тут считать
нечего: ход — это две клетки, и сервер просто прикладывает его теми же
правилами. Сверки отпечатков, как в бильярде, поэтому нет: клиенту нечего
пересчитывать.

ХОД — ЭТО ОДИН ПРЫЖОК, а не вся цепочка. По сети едет `{ from, to }`, и если
побившая шашка может бить дальше, ход остаётся у неё — ровно как «попал —
стреляй ещё» в морском бое. Так соперник видит цепочку по шагам, а не готовую
доску с четырьмя пропавшими шашками, и так же устроен ввод: кликают клетку за
клеткой, а не набирают `d4:f6:h4` одним движением.

Правила именно РУССКИЕ, и три места отличают их от международных и английских:
простая бьёт назад, дамка летает и бьёт на расстоянии, а простая, дошедшая до
последнего ряда ПОСРЕДИ боя, немедленно становится дамкой и бьёт дальше уже
дамкой (в международных она обязана остановиться). Бить обязательно, но
большинство — НЕТ: какой из боёв выбрать, решает игрок, даже если он берёт одну
вместо трёх. Поддавков, столбовых и доски 10×10 нет сознательно — это домашние
правила, о которых за одним столом договариваются вслух, а в пасхалке они дают
только споры «а у нас так не играют».

Отдельно стоит ТУРЕЦКИЙ УДАР: побитые шашки снимаются не сразу, а в конце
цепочки, и перепрыгнуть уже побитую нельзя — она стоит на доске и мешает. Это не
мелочь: на нём держится половина комбинаций. Поэтому побитые лежат в
`state.captured`, а окно рисует их ПОГАШЕННЫМИ — правило видно глазами, а не
читается в справке.

Ничья в шашках — законный исход, и она единственная на все пасхалки. Отсюда две
вещи, которых больше нигде нет: счётчик простоя `IDLE_PLIES` (пятнадцать ходов
каждой стороны без взятий и без ходов простыми — иначе две дамки ходят друг
вокруг друга бесконечно, тот же довод, что `STALL_BOUTS` в дураке) и третья
колонка в таблице очков. На МЕСТО в таблице ничьи не влияют сознательно: считать
ничью половиной победы значит поощрять размен до голых дамок.

Сложность бота (`shared/checkersBot.js`) — это ГЛУБИНА СЧЁТА, как в дураке и
морском бое, а не дрожь руки, как в бильярде: исполнять в шашках нечего, ход —
это две клетки. Новичок считает на полход, Любитель на три, Мастер на пять; и
Новичок ЕДИНСТВЕННЫЙ, кто обрывает счёт посреди размена — остальные досчитывают
начатый бой до конца. Это и есть беда живого новичка: он радуется съеденной
шашке ровно за полхода до того, как её съедят обратно. Уровни стережёт
`shared/checkersBot.test.js`, и турнир там маленький нарочно: разрыв между
уровнями огромный, а партия на глубине пять считается секунду.

Доска РАЗВОРАЧИВАЕТСЯ своим цветом вниз, как за настоящим столом. Картинок у неё
шесть — две клетки и четыре шашки, — и подключаются они ПО ИМЕНИ ФАЙЛА, как арт
карт в рогалике: `frontend/src/assets/checkers/{light,dark,man-light,man-dark,king-light,king-dark}.png`,
таблицы соответствия нет нигде. Клетки и шашки включаются ПОРОЗНЬ: нарисованная
доска с кружками из вёрстки выглядит непривычно, но работает, а половина шашек
картинками и половина кружками — это уже сломанная игра. Файлов нет вовсе —
клетки рисуются цветом, шашки кружками с короной; это рабочее состояние, а не
поломка.

ШАШКИ ЗДЕСЬ КАРТИНКИ, А ШАРЫ В БИЛЬЯРДЕ — ВЁРСТКА, и разница не в настроении:
шару нужен НОМЕР, а нарисованный номер на кружке в двадцать пикселей не
читается. Шашке номер не нужен, зато нужна ТОЛЩИНА — дамка в русских шашках это
две шашки друг на друге, и на присланных картинках она так и нарисована; кружок
с короной поверх рядом не стоял. Отсюда же следует, что подсветка (выбранная
шашка, подсказка «бить обязательно») живёт НА КЛЕТКЕ, а не на шашке: шашка —
картинка с прозрачными углами, и рамка вокруг неё обвела бы квадрат вместо
кружка. Картинка клетки НАТЯГИВАЕТСЯ на клетку целиком
(`background-size: 100% 100%`), а из присланного листа она вырезается квадратом
по центру: у нарисованных текстур светлая и тёмная клетки почти никогда не
совпадают по размеру пиксель в пиксель, а доска из клеток разного размера
разъезжается. Лист, скрипт нарезки и требования к картинкам —
`design/checkers-board/README.md`.

DOOM — единственная пасхалка, которую мы не писали. Это настоящий DOOM 1993 года:
prboom, собранный в wasm проектом webDOOM, шароварный `doom1.wad` и звуки —
`design/doom/README.md`. Отличается он от остальных двенадцати не тем, что чужой,
а тем, что про него НИЧЕГО НЕ ИЗВЕСТНО: правил в `shared/` нет, партию никто не
считает и не проверяет, наружу игра отдаёт только пиксели на холсте. Отсюда
главное: МИНИ-ТОПА У DOOM НЕТ и не будет — «рекорд», посчитанный по картинке,
был бы выдумкой. Пасхалка тут ровно в том, что DOOM запускается прямо на рабочем
месте, и этого достаточно.

Из чужого движка следуют три вещи, которых нет ни у кого. Первая: ЭКЗЕМПЛЯР ИГРЫ
ОДИН НА ВКЛАДКУ И ЖИВЁТ ДОЛЬШЕ ОКНА. Закрыли — холст вынимается из разметки,
главный цикл встаёт на паузу, игра остаётся как была; отдать своё состояние
наружу, как это делают тетрис и маджонг, DOOM не умеет. Второй экземпляр не
создаётся и по другой причине: SDL вешает слушатели на window и не снимает их
никогда, а куча — 256 МБ. Вторая: КЛАВИАТУРА уходит в игру, только пока холст в
фокусе, — SDL по умолчанию слушает document и гасит preventDefault-ом всё подряд,
и с таким слушателем после закрытия окна на сайте перестали бы печататься буквы.
Третья: Escape НЕ ЗАКРЫВАЕТ окно, в отличие от всех остальных пасхалок, — в DOOM
это клавиша меню.

Полноэкранного режима у DOOM нет сознательно, и из этого следует мышь. В этой
сборке SDL просит захват указателя ТОЛЬКО в полноэкранном режиме, то есть без
него мышь не работала бы вовсе — поэтому захват включает окно само
(`elementPointerLock`): клик по холсту, дальше SDL считает движения из
`movementX`. Пока указатель не захвачен, поверх холста висит подсказка, иначе
игра выглядит сломанной: клавиши работают, мышь нет. Обратная сторона захвата —
под ним ЛЮБОЙ клик достаётся холсту, и крестик закрытия недостижим, пока мышь не
отпущена тем же Escape.

Настройки игре кладутся файлом (`prboom.cfg`) до старта, и меняются в нём ровно
четыре вещи: вертикаль мыши (в DOOM это ход вперёд-назад, а не взгляд — с мышью,
которой целятся, это «шагнул в лаву, потому что прицелился ниже»), «вперёд» на
правой кнопке, полноэкранный режим и разрешение. Всё остальное — WASD, огонь на
мыши, пробел «открыть» — вкомпилировано в саму сборку webDOOM, а не задано нами.

Мини-топы — единственное, что пасхалки вообще хранят в базе: таблицы
`tetris_scores`, `troika_scores` и `solitaire_scores` (миграции
`025_tetris_scores.sql`, `026_troika_scores.sql`, `027_solitaire_scores.sql`), по
ОДНОЙ строке на игрока — его рекорд. Историю партий не пишем: топ показывает
лучший результат, а тысячи строк «партия на 300 очков» не нужны никому. Таблицы
отдельные, а не одна общая с колонкой игры: показатели в подписи строки у игр
разные (линии и уровень против ходов, часов и каскада), и общая таблица
неизбежно стала бы набором полей, половина из которых всегда NULL. У пасьянса к
тому же рекорд — МИНИМУМ: там соревнуются временем, поэтому в его таблице `LEAST`
вместо `GREATEST` и `ASC` в индексе.

Так же устроен и `mahjong_scores` (миграция `037_mahjong_scores.sql`): рекорд —
время разобранного стола, то есть снова минимум, а рядом лежит число
перемешиваний. Перемешать в маджонге можно только в тупике, поэтому ноль в этой
колонке — честная строчка в подписи рекорда, а не украшение.

Туда же относится `roguelike_scores` (миграция `034_roguelike.sql`), с одной
особенностью: рекорд там — ПАРА (пройденных циклов, пройденных узлов). Циклы —
то, ради чего в эту игру играют, но мера грубая: два забега «по два цикла»
отличаются тем, где именно каждый умер на третьем. Отсюда сравнение строк
Postgres в upsert (`(EXCLUDED.loops, EXCLUDED.floor) > (…)`) и составной индекс.

У бильярда в базе не рекорд, а СЧЁТЧИК (`pool_scores`, миграция `028_pool.sql`):
победа — очко. Рядом хранятся и поражения — они не влияют на место, но
показываются («12 / 4»): одно очко за победу поощряет количество, и без второго
числа сыгравший сорок партий обгонял бы выигравшего восемь из десяти. Эло не
берём — в офисе оно только запутает. Там же лежит `pool_games` — партия целиком,
и нужна она ровно потому, что сервер тут арбитр. Брошенную партию можно забрать
себе через сутки без хода соперника, а сдаться — кнопкой: иначе проигрывающему
выгодно просто закрыть вкладку.

У морского боя в базе ровно то же, что у бильярда (`battleship_scores`, миграция
`035_battleship.sql`), и партия целиком там же (`battleship_games`), потому что
арбитр опять сервер. Игроки — два столбца `p0`/`p1`, а не массив, как в дураке: в
морской бой играют строго вдвоём, и массив из двух элементов означал бы «когда-нибудь
тут будет четверо», чего не будет.

У шашек там же и почти то же (`checkers_scores`, миграция `038_checkers.sql`,
партия целиком в `checkers_games`), но с колонкой, которой нет ни у кого:
НИЧЬИ. Ни в одной другой пасхалке ничьей не бывает вовсе, а в шашках это
законный исход — показывать её надо. Место в таблице она при этом не двигает
(см. выше).

У дурака в базе то же самое (`durak_scores`, миграция `033_durak.sql`) и по той
же причине, с одной поправкой из правил: проигравший там ровно один — тот, у
кого остались карты, — а победителей за столом на четверых бывает трое, поэтому
поражение пишется одной строкой, а победы всем остальным. Ничья (вышли разом или
карты пошли по кругу) не пишется вовсе: дурака не было. Партия целиком лежит в
`durak_games`, и игроки там МАССИВОМ, а не колонками `p0`/`p1`, как в бильярде:
место в массиве и есть место за столом, и из него же берётся, кто чей сосед.

Тройка — единственная игра со своей экономикой: таймер идёт вниз, а часы на поле
его продлевают, поэтому очки берутся не с тройки (она стоит 30), а с каскадов и
собранных по пути «штучек» — ракеты за четыре фишки разом, бомбы за шесть,
призмы за восемь. Сложность растёт уровнем: чем больше очков, тем реже сыплются
часы, и любая партия рано или поздно кончается — иначе бесконечный режим
сравнивал бы в топе терпение, а не игру.

Поверх этой экономики в тройке идут МИНИ-ЗАДАНИЯ: в случайный момент приходит
короткое условие со своим таймером («разбить 14 звёзд», «собрать трое часов»,
«довести цепочку до ×5»), а за него дают очки, ×2 на все получаемые очки на
двадцать секунд или секунды в банк времени. Смысл в подмене цели: без задания
матч-3 на время — это поиск любого хода побольше, а с ним ход, который сам по
себе хуже, вдруг становится правильным. За провал НЕ отнимается ничего — поле
игрок не выбирает, в отличие от хода. Правила (условия, награды, зачёт) — раздел
«Мини-задания» в `shared/troika.js`, панель сбоку от поля — `renderQuest` в
`frontend/src/troika.js`; на узком экране панель переезжает НАД полем.

Из заданий следует единственная неочевидная вещь на сервере: границы
правдоподобности (`isPlausibleRun`) считаются с учётом наград — счёт удваивается
под ×2 и растёт на очки за задания, а длина партии — на выданные ими секунды.
Число заданий в партии ограничено паузой между ними (`maxQuests`), иначе «задание
дало девять тысяч» пришлось бы принимать на слово сколько угодно раз.

Шаг цепочки в тройке ПОКАЗЫВАЕТСЯ ФАЗАМИ (`playStep` в `frontend/src/troika.js`):
вспыхивают засчитанные фишки → исчезают → на их месте всплывают очки → сверху
всё съезжает в дырки. Правила считают тот же шаг целиком и мгновенно, поэтому в
DOM до последней фазы висит старая картинка — она и нужна, чтобы показать, что
именно исчезает. Таймер на время фаз СТОИТ: игрок в этот момент не может сделать
ничего, и длинная цепочка (лучшее, что бывает в этой игре) иначе наказывала бы
сильнее всего.

Собирается в тройке не «линия», а СВЯЗНАЯ ОБЛАСТЬ одного вида, внутри которой
есть фигура — линия из трёх или квадрат 2×2. Убирается область целиком, вместе с
прилипшими по краям одиночками: игрок видит на поле пятно одного вида, а не «вот
эти три в счёт, а четвёртая сбоку — нет». По той же причине награду считает ЧИСЛО
убранных фишек области (`ROCKET_TILES`, `BOMB_TILES`, `PRISM_TILES`), а не их
форма: четыре фишки разом — ракета, как бы они ни легли. Пороги бомбы и призмы
подняты (6 и 8) как раз потому, что пятно набирается легче линии. Две фигуры
сильнее своего размера и названы отдельно — пятёрка в ряд даёт призму, а
пересечение линий (угол, Т, крест) бомбу: их строят намеренно.

Если игрок несколько секунд не ходит, окно подсвечивает пару, которую можно
обменять (`findMove` возвращает всегда один и тот же ход на одном и том же поле —
подсказка не должна прыгать).

Фишки тройки — единственная в проекте игровая ГРАФИКА (у остальных пасхалок всё
рисуется вёрсткой и SVG). Тридцать шесть картинок (6 видов × 6 состояний) лежат
одним спрайтом `frontend/src/assets/troika-tiles.webp`, а строка и столбец в нём
считаются прямо из констант `shared/troika.js` — таблицы соответствия «код →
картинка» нет нигде, поэтому **порядок `KINDS` и значения `NONE…CLOCK` менять
нельзя, не пересобрав спрайт**. Исходники и команда пересборки —
`design/troika-tiles/README.md`.

Пасьянс — обычная косынка ПО ОДНОЙ КАРТЕ и с бесконечными перекладываниями
колоды, и это выбрано под топ: соревнуются ВРЕМЕНЕМ, а по три карты со счётом
заходов половина раскладов не разбирается вовсе — в топе сравнивалось бы «кому
досталась разбираемая раздача». Отмены хода нет по той же причине: партия на
секундомере, а отмена превращает её в «тыкаю, пока не выйдет». В базу уезжают
ТОЛЬКО разложенные партии: у брошенной раскладки времени нет.

Секундомер пасьянса идёт, только пока играют: он заводится первым ходом, встаёт
на свёрнутой вкладке и на закрытом окне (партия сохраняется и открывается с того
же места), и ОСТАНАВЛИВАЕТСЯ на кнопке «Сложить» — когда закрытых карт не
осталось, партия уже выиграна, а автосбор это показ, а не игра.

Карты пасьянса — вторая (после фишек тройки) игровая графика: лист 13×4
`frontend/src/assets/cards-8bit.png` плюс отдельная рубашка `card-back.png`.
Строка и столбец в листе считаются прямо из правил (`suitOf` и `spriteCol` в
`shared/solitaire.js`), таблицы соответствия нет нигде, **менять порядок мастей
и достоинств нельзя, не заменив картинку** (туз в листе стоит в КОНЦЕ ряда).
У карт нарисован только верхний слой на прозрачном фоне — белую подложку со
скруглением рисует CSS. Исходники и раскладка — `design/cards/README.md`.

Внутри сапёра есть вторая пасхалка: набранное в окне игры слово `vok` (в русской
раскладке те же клавиши дают `мщл`) включает в панели кнопку «%», а она пишет на
закрытых клетках шанс мины. Считает его `frontend/src/minesweeperOdds.js`
перебором расстановок — **по открытым цифрам и остатку мин, то есть по тем же
данным, что видит игрок**. Это принципиально: раскладку сервер по-прежнему не
отдаёт, и режим не должен превращаться в «покажи мины» — он показывает шансы, с
которыми игрок и так играл. Флажки в расчёт не берутся сознательно: они могут
быть ошибочными, а вероятность, выведенная из чужой ошибки, бесполезна.

## Факультеты (распределяющая шляпа)

В профиле есть тест на факультет Хогвартса — Гриффиндор, Слизерин, Когтевран,
Пуффендуй. Пройти его можно **один раз в жизни аккаунта**, дальше факультет
закреплён: ручки «пройти заново» нет ни у пользователя, ни у модератора, а
вставка результата идёт через `ON CONFLICT DO NOTHING` (миграция
`029_faculty.sql`). Это не настройка профиля, которую крутят, пока не выпадет
любимая.

Где виден результат: плашка перед ником (**сначала роль `mod`, потом факультет**
— права важнее), «подложка» обложки профиля под цвета дома и карточка с
качествами в профиле. В топе по записям строка тоже красится, **но первое место
всегда золотое** — правило `.top-row.faculty-tint:not(.top-row-gold)`.

| Что | Где |
|---|---|
| Описания домов, префиксы, тексты карточек | `shared/faculties.js` |
| Вопросы, шкалы, эталоны, подсчёт | `backend/src/faculty/quiz.js` (+ тесты рядом) |
| Хранение, джойн факультета к спискам | `backend/src/faculty/store.js` |
| API | `backend/src/routes/faculty.js` |
| Окно теста и карточка | `frontend/src/faculty.js`, песочница `frontend/dev-faculty.html` |
| Гербы домов (картинки) | `design/faculty-crests/README.md` → `assets/faculty-*.png` |
| Плашки перед ником (роль + факультет) | `frontend/src/namePrefix.js` — ОДНО место на весь сайт |

Устройство теста и почему оно такое — в шапке `quiz.js`, коротко:

- ответы **не знают про факультеты**. Каждый вариант двигает четыре шкалы
  (смелость, амбиции, ум, верность), а дом выбирается в самом конце ближайшим
  эталоном. Иначе человек на третьем вопросе понимает раскладку и отвечает не
  про себя, а про желаемый результат;
- **веса не уезжают в браузер**: клиент получает вопросы без них, считает
  сервер по сохранённым ответам;
- у каждого вопроса варианты уравновешены (сумма весов по каждой шкале = 0),
  порядок вопросов свой у каждого аккаунта и не меняется между заходами;
- вес у варианта либо **есть, либо нет** (только −1, 0, +1). Полутона —
  «наполнители» ±1 в довесок к основным ±2 — один раз уже сломали тест: ими
  удобно доводить сумму вопроса до нуля, и по уму с амбициями таких довесков
  набралось 86% и 77%, почти все в минус. Первые четверо получили ум от 0 до
  −65, трое из четырёх — один и тот же дом. Тест мерил не характер, а
  скромность;
- черновик помнит **версию опросника** (отпечаток от самих вопросов, миграция
  `030_faculty_quiz_version.sql`): после переписывания вопросов недопройденный
  тест выбрасывается, иначе старые ответы молча уехали бы под новые вопросы;
- вопросы **не про работу** — обычные житейские развилки. Рабочие ситуации,
  выдуманные со стороны, первый же человек с поста узнал бы как фальшь.

Прогресс живёт **на сервере**, а не в localStorage, и ответ сохраняется по
одному сразу (`POST /api/faculty/answer`): тест проходят на работе, посреди
него звонят, вкладку сворачивают — вернуться нужно на тот же вопрос и с другого
устройства тоже.

Правки вопросов и эталонов **обязательно** прогонять
`node --test backend/src/faculty/quiz.test.js`: половина тестов там
статистическая (все дома достижимы, никто не забирает половину людей, характер
по ответам восстанавливается, шкалы не слиплись), и одно неудачное число ломает
их молча. Главный из них — «перекос населения не сгоняет всех в один дом»:
он проверяет не арифметику вопросов, а то, что даже смещённое по какой-то шкале
население расходится по всем четырём домам. Именно этого теста не хватало,
когда тест сломался в первый раз.

## Поиск клиента в CRM («Клиент» на главной)

Третий режим строки поиска, рядом с «Поиск» и «Теги»: телефон или гос. номер —
и ОДНА карточка человека из CRM. Имя, баллы, машины, все обслуживания и
содержимое каждого чека.

Затевалось это ровно из-за одного: в самой CRM путь до «что этому клиенту
делали» — четыре страницы, и КАЖДЫЙ чек там отдельная ссылка, которая грузится
секундами. Оператор с трубкой в руке столько не ждёт. Поэтому сайт обходит чеки
САМ, фоном и по одному, а до готовности показывает на их месте плейсхолдеры:
список обслуживаний виден сразу, содержимое дозаполняется на глазах.

| Что | Где |
|---|---|
| Разбор трёх страниц CRM и маски ввода | `shared/crmClients.js` (+ тесты рядом) |
| Прокси под персональной сессией | `backend/src/routes/crm.js` (`/clients`, `/clients/:id`, `/sales/:id`) |
| Строка поиска и карточка | `frontend/src/clientSearch.js`, `clientSearch.css` |
| Песочница без CRM и без базы | `frontend/dev-client.html` (`npx vite` → `/dev-client.html`) |

Страницы CRM, из которых всё собирается: `/dial_clients/?phone=…&vehicleNumber=…`
(поиск), `/clients/N` (панель клиента + таблица его продаж), `/sale/N` (позиции
чека). API у CRM нет, поэтому разбор — regex по разметке, как и в
`crmAnalyse.js`; фикстуры в тестах сняты с реальных страниц.

Что тут стоит помнить при правках:

- **«сессии нет» узнаётся ПО ФОРМЕ ЛОГИНА** (`parseLoginForm`), а не по
  приметам `/analyse/free`. `parseAnalyseFree(...).loginPage` считает логином
  всё, где нет ни фильтра станций, ни таблицы товаров, — а этого нет ни на
  `/dial_clients/`, ни на `/clients/N`, ни на `/sale/N`. Пока `fetchPage`
  спрашивал у него, живая сессия объявлялась мёртвой, куки стирались, и поиск
  клиента отвечал «войдите в CRM» — в том числе сразу после успешного входа;
- **обход чеков делает ФРОНТ, а не сервер.** Очередь запросов к CRM
  последовательная (`backend/src/crm/client.js`), и «прочекать всё сразу»
  одним ответом означало бы держать запрос открытым минуту. Вместо этого фронт
  просит чеки по одному (три в полёте) и рисует их по мере готовности;
- **обходятся только ПОКАЗАННЫЕ обслуживания** (`SALES_PAGE`, по восемь, дальше
  «показать ещё»). У постоянного клиента чеков под полсотни, очередь к CRM
  последовательная — «прочекать все» это минута ожидания ради строк, до которых
  разговор не дойдёт. «Показать ещё» дозаказывает добавленные;
- **карточка не выше окна.** Страница поиска не прокручивается вовсе
  (`#page-search { overflow: hidden }`), и высокая карточка просто обрезалась с
  двух сторон. Прокручивается ВНУТРИ неё список обслуживаний, шапка с именем и
  полоска итогов остаются на виду;
- **у строки обслуживания ровно две строки текста**, обе с многоточием: что
  делали и где. Станция в CRM — это адрес, вписанный руками («деревня
  Новосаратовка Свердловское городское поселение 267А»), и от переносов список
  переставал читаться столбцом. Служебные слова адреса выкидываются при показе
  (`shortStation`), полный адрес остаётся в подсказке;
- **чек кэшируется на часы, а клиент — на минуты.** Закрытый чек не меняется
  никогда, а баллы оператор смотрит, пока разговаривает;
- **упавший чек не рвёт обход остальных** — у строки появляется «чек не
  загрузился» и кнопка повтора;
- **маски позиционные и живут в `shared/`**, а не в окне: «что такое правильный
  телефон и правильный гос. номер» — то же знание, которым запрос проверяется
  перед походом в CRM. Латиница в гос. номере молча превращается в кириллицу
  (`k926aa147` → `К926АА147`): раскладку ради номера никто не переключает;
- **у маски тестируется НАБОР, а не только формат** (`maskedFieldEdit`). Номер
  не только печатают: его стирают, правят в середине и вставляют из буфера.
  Отдельно ловится Backspace по дорисованному разделителю: человек видит
  «+7 (921)», жмёт стереть, браузер убирает скобку, маска возвращает её на
  место — и поле выглядит намертво застрявшим. Признак такого удаления —
  значащих символов не убавилось;
- **кнопки «найти» нет.** Поле — та же «таблетка» с лупой, что и главный поиск
  (`.search-box`), и ищет так же само: главный по мере ввода, этот — как только
  номер набран целиком (ходить в CRM по половине номера незачем);
- **`01.12.-0001` в дне рождения — это «не заполняли»**, а не дата. Показывать
  такое оператору нельзя, `parseClientCard` отдаёт `null`;
- **чеки разворачиваются к свежим вперёд** (`crmStampValue`): CRM отдаёт их по
  возрастанию, а разговор начинается с последнего визита. Сравнивать отметки
  времени CRM строками нельзя — «28.07.2026» лексикографически меньше
  «07.02.2024»;
- **номера показываются знаком, а не строкой**: оператор сверяет их с тем, что
  ему диктуют в трубку. Список номеров — объединение панели клиента (туда
  вписывают руками) и номеров из чеков (там проставляется на месте);
- **все значки — SVG, эмодзи нет ни одного** — как в сапёре и морском бое.
  Эмодзи рисует операционная система, в каждой по-своему, и подогнать его под
  размер строки, под тему и под цвет нельзя никак: звезда баллов золотая в
  шапке и зелёная у начисления — это один значок с `currentColor`.

Нет сессии CRM — карточка показывает маленькую форму входа прямо на месте, а не
отсылает за панелью наличия на страницу машины: человек искал клиента.

## Лента изменений машины («Что изменили»)

Под страницей машины лежит лента правок (`car_events`), а клик по карточке
правки открывает окно с разбором. В базе хранится сырьё —
`changed_fields = { поле: { from, to } }`, где значением бывает и число, и
объект вроде `{"mf":{"part":"LO-1901","absent":false}}`. Окно раньше показывало
его как есть: два JSON'а, зачёркнутый и зелёный. Увидеть в них, что поменялся
ОДИН салонный фильтр, было нельзя.

Разбор сырья в человеческий список — `shared/carDiff.js` (тесты рядом), вёрстка
окна и ленты — `frontend/src/carPage.js`, песочница без бэкенда —
`frontend/dev-diff.html`. Что стоит помнить:

- **группа = вкладка окна правки** (`carEditor.js`): правил «Фильтры ДВС» —
  ищет в изменениях «Фильтры ДВС», а не имя колонки в базе;
- **объект разворачивается по составным частям**, и в списке остаются ТОЛЬКО
  изменившиеся: неизменившийся масляный фильтр из окна пропадает совсем;
- **`absent:true` и пустой артикул — разные строки**: «фильтра у машины нет»
  против «не заполнено». Подписи фильтров (vf — воздушный, mf — масляный,
  sf — салонный) стоят на отдельном тесте: перепутанная означает неверный
  артикул у оператора;
- **поле, у которого значение не изменилось, в список не идёт**: в
  `changed_fields` попадает и `'2019' → 2019` (numeric Postgres отдаёт строкой),
  а строка «было 2019 → стало 2019» заставляет искать разницу, которой нет.
  Такие поля считаются числом внизу окна, а не выбрасываются молча;
- **изменение, которое разобрать не вышло** (незнакомый ключ, чужое поле),
  показывается сырьём в «Прочем» — пропасть из окна оно не должно;
- подписи изменённых полей висят и на карточке в ленте: у машины правят по
  одному полю, и ради «мощность» открывать окно незачем.

## Особенности автомобилей из CRM

Список «этой машине так не делаем» живёт ОДНИМ файлом — `shared/crmQuirks.js`.
Оттуда его берут страница машины (секция «Особенности из CRM»), калькулятор на
сайте и юзерскрипт (плашки на карточках агрегатов), а `shouldDefaultToPartial()`
в `shared/calculator.js` — только следствие этого списка. Новое правило из CRM
добавляется туда, а не копией в UI.

Формулировки: **«аппаратная замена» в CRM = «полная»**. Если аппарат подключить
некуда — нельзя писать «замену не делаем»: частичную делаем всегда, и текст
правила обязан это говорить, иначе оператор откажет клиенту целиком (тест
`crmQuirks.test.js` это проверяет).

## Подбор масла: три источника требований, и они не спорят

Разбор и обоснование — `docs/DOPUSKI.md`. Коротко, что откуда берётся:

1. **Допуска машины** (`car_approvals`) — это паспорт РЕКОМЕНДОВАННОГО МАСЛА, а
   не требования мотора: у 95% машин там допуска трёх и более чужих марок.
   Значение имеют только родные марке (`shared/approvals.js`).
2. **Продукты Motul по этой машине** — второй источник, дополняет первый.
3. **Правило «марка + годы + топливо»** (`shared/oemRules.js`) — для машин, у
   которых допусков нет вовсе (каждая пятая).

Граница между ними жёсткая, и её нельзя размывать: правило применяется как
требование ТОЛЬКО там, где родного допуска нет ни в списке, ни у Motul, — они
никогда не работают одновременно. Единственное, что правило говорит всегда, —
есть ли у машины сажевый фильтр: это железо, а не строка в списке.

Новое знание о требованиях завода добавляется в `oemRules.js` строкой допуска
из справочника `approvals.js`, а не отдельной веткой в подборе.

## Осторожно: обозначения фильтров

В данных и в импорте (`extractFilters` в `scrape-filters.js`, `shared/crmAnalyse.js`):

- `vf` — **воздушный** (артикулы MANN `C …`);
- `mf` — **масляный** (`W …`, `HU …`);
- `sf` — салонный (`CU …`, `CUK …`, `FP …`).

Подписи в скобках на карточке машины (`frontend/src/carPage.js`) и в
калькуляторе юзерскрипта им противоречат — им верить нельзя, эталон здесь.
Прежде чем писать любой код, который переносит или сравнивает фильтры, сверься
с этим списком: перепутанное поле означает неверный артикул у оператора, а это
хуже пустого поля.

## Геометрия интерфейса

Скругления берутся ТОЛЬКО из шкалы в `:root` (`frontend/src/style.css`).
Числом радиус в новом коде не пишется — ни разу.

| Токен | | Роль |
|---|---|---|
| `--r-1` | 4px | метка внутри строки: бейдж, тег, код |
| `--r-2` | 8px | контрол: кнопка, поле, чип, селект |
| `--r-3` | 12px | карточка, блок, панель списка |
| `--r-4` | 16px | крупная поверхность: окно, вход, плитка |
| `--r-round` | 999px | капсула: пилюля, тумблер, полоса прогресса |
| `--r-circle` | 50% | круг: аватар, точка, радио |

Ступень выбирается **по роли элемента, а не по его размеру на глаз**. До шкалы
в проекте было 25 разных значений на 385 объявлений, а токен `--radius`
использовался десять раз из них: радиус каждый раз назначался заново.

Радиус — свойство МАТЕРИАЛА, а не украшение. На углу сильнее всего видно, как
поверхность ловит свет, и панели со скруглениями 5, 7, 9, 11 и 14 читаются не
как «разные скругления», а как разные материалы на одном экране.

**Пятой ступени быть не должно.** Как только их становится больше, чем
помещается в голове, возвращается прежнее «тут поставлю 11, а тут смотрится
лучше 13». Нужен промежуточный радиус — значит роль элемента определена
неверно, а не шкала коротка.

Капсула и круг — **не ступени**, а формы, и от шкалы не зависят: капсула это
всегда половина высоты, круг — половина стороны. Тумблер, полоса прогресса и
пилюля — капсулы; аватарка, точка и радиокнопка — круги. Радиус, равный
половине высоты элемента, это `--r-round`, а не «очень большая ступень».

Своя геометрия остаётся у игр (клетка сапёра, карта пасьянса, фишка маджонга
подогнаны под спрайт и сетку), у boot-экрана (резкие углы там — стиль), у
теплокарты активности и полосок загрузки боксов (клетка в 2–3 пикселя) и у
виджетов leaflet. Шкала их не касается.

### Отступы

Та же история и та же строгость: `--s-1` 4px · `--s-2` 8 · `--s-3` 12 ·
`--s-4` 16 · `--s-5` 24 · `--s-6` 32 · `--s-7` 48 · `--s-8` 64.

Ступеней вдвое больше, и это не противоречие. Радиус — свойство МАТЕРИАЛА,
их должно быть мало, иначе поверхности перестают быть одной. Отступ — РИТМ, и
ему нужен диапазон от зазора между иконкой и словом до воздуха между секциями.

До шкалы было 868 объявлений тридцатью значениями, больше половины не кратны
четырём (8, 10, 6, 12, 14) — то есть шаг фактически двухпиксельный. Двух
пикселей глаз не читает как «тут теснее», он читает их как неаккуратность.

Округляли к ближайшей ступени, а **на равном расстоянии — вверх**: 6 → 8,
10 → 12, 20 → 24. Сайту не хватает воздуха, а не тесноты.

Не трогали две категории, и обе — не ритм:

- **≤3px** — волосяная подгонка (`padding: 1px 6px` у бейджа), ступень её
  раздувает;
- **отступ, РЕЗЕРВИРУЮЩИЙ МЕСТО** под что-то. `padding-left: 46px` у
  `#search-input` — это место под лупу, `padding-right: 30px` у `.lead-select`
  — под стрелку, `margin-left: 64px` у `.rc-lanes-heads` держит шапки в створе
  с колонками ленты записей. Сдвинешь — разъедется то, под что оставлено.
  Признак: одиночный горизонтальный отступ ≥20px или сильно разные бока.

Смотреть и спорить — `frontend/dev-geometry.html` (`npx vite` →
`/dev-geometry.html`): настоящие классы сайта по ступеням, живые ползунки
радиусов и один множитель «воздуха» на все отступы сразу — ритм это
соотношение ступеней, и крутить их порознь значит его ломать. На живом сайте
этого не посмотреть — он за входом и за базой.

## Акцентный цвет: пользователь крутит ТОН, а не цвет

В профиле («Оформление») есть выбор акцента: девять готовых тонов и ползунок
на всё остальное. Наружу уходит **одно число — тон в градусах**, и это главное
решение всей затеи.

Светлота и насыщенность остаются нашими. Причина не в жадности: от светлоты
зависит, каким цветом читается надпись ПОВЕРХ акцента (`--accent-fg` — почти
чёрный в тёмной теме, белый в светлой). Отдай светлоту пользователю — и
половина выбранных цветов даст кнопку с нечитаемым текстом. Тон на контраст не
влияет вовсе, поэтому его можно отдать целиком.

Проверено, а не обещано: `frontend/src/accentContrast.test.js` перебирает все
360 тонов и требует WCAG AA (4.5:1). Худший тон даёт **9.09:1** в тёмной и
**4.89:1** в светлой. Числа тест берёт **из `style.css`**, а не переписаны в
него копией, — правка светлоты «на глаз» обязана ронять тест, а не молча
портить кнопки.

Из фиксированной светлоты следует и то, что синий с красным выйдут бледнее
жёлтого: на L=0.80 они просто не бывают такими насыщенными, и браузер сам
приведёт цвет в охват, **убавив насыщенность и сохранив светлоту**. Это ровно
то, что нужно, — контраст надписи не поедет.

| Что | Где |
|---|---|
| Хранение, пресеты, разметка и привязка выбора | `frontend/src/accent.js` |
| Токены `--accent-h` / `--accent-hh` и всё, что от них считается | `frontend/src/style.css` |
| Граница контраста (тест) | `frontend/src/accentContrast.test.js` |
| Песочница: что красится, а что нет | `frontend/dev-accent.html` |

Устройство — как у темы (`theme.js`), и это не подражание: выбор так же лежит
в localStorage и так же применяется **инлайновым скриптом в `<head>`** до
загрузки CSS. Иначе на каждой загрузке сайт на кадр вспыхивал бы жёлтым — та
же «мигающая тема», только цветом. Хранится **на устройстве, а не в аккаунте**,
ровно как тема; в базе для акцента ничего нет.

Что стоит помнить при правках:

- **`--accent-hh` — тон акцента В ЭТОЙ ТЕМЕ.** В светлой он на 21° ниже: тот
  же тон на низкой светлоте читается не «оранжевым», а болотным, и светлая
  тема с самого начала жила на 62°, а тёмная на 83°. Смещение сохраняет
  сегодняшний вид обеих тем при значении по умолчанию;
- **смещение считает `accent.js` и кладёт готовым числом** в `--accent-h-light`,
  а не `calc()` в CSS. Пользовательские свойства — поток токенов, а не числа:
  `calc()` внутри них НЕ вычисляется, `getComputedStyle` отдаёт «calc(83 - 21)»
  этой самой строкой, и сфера на главной (канвас, ей нужно настоящее число)
  получала бы вместо тона мусор;
- **сфера красится тем же тоном** (`sphere.js`): это первое, что видно на
  главной, и оставить её жёлтой на синем сайте значит показать поломку на
  первом же экране. Светлота у её узлов своя — «ближний» узел заметно темнее
  кнопки того же тона;
- **oklch в канвасе разбирается рисованием пикселя**, а не чтением `fillStyle`
  или `getComputedStyle`: оба отдают `oklch()` обратно той же строкой. Красим
  1×1 и читаем `getImageData` — заодно даром достаётся приведение в охват;
- **образцы в выборе красятся ТОЙ ЖЕ формулой**, что и кнопки, только тон
  берут из собственного `--sw-h`. Поэтому в светлой теме они сами становятся
  бронзовыми: человек видит цвет, который получит. Считать их в JS значило бы
  держать формулу в двух местах;
- **вендорные псевдоэлементы дорожки ползунка разведены по разным правилам.**
  Селектор с незнакомым псевдоэлементом браузер считает недействительным
  ЦЕЛИКОМ, и `-webkit-…, -moz-…` одной строкой не срабатывает нигде.

### Что акцентом НЕ красится, и это осознанно

- **золото топа** — медаль за первое место; синяя медаль не медаль;
- **зелёный, красный, синий** — это СМЫСЛ (свободно, ошибка, ссылка), а не
  украшение: перекрасив их, мы сломаем чтение статусов;
- **цвета факультетов** — Гриффиндор красный по определению;
- **небо и солнце в переключателе темы** — тумблер рисует ДЕНЬ И НОЧЬ, а не
  поверхность сайта: небо синее, солнце жёлтое, и меняться вместе с акцентом
  им незачем.

Посмотреть и поспорить — `frontend/dev-accent.html` (`npx vite` →
`/dev-accent.html`): рядом с ползунком живые контролы сайта и та самая золотая
строка топа, которая обязана остаться золотой.

## Фон главной: сфера или трубы

На главной под строкой поиска крутится заставка, и их ДВЕ на выбор: сфера из
машин (как было) и трубы — тот самый хранитель экрана из Windows 95. Ручка — в
профиле, в разделе «Оформление», прямо над выбором акцента; выбор лежит в
localStorage, то есть НА УСТРОЙСТВЕ, а не в аккаунте, ровно как тема и акцент.

| Что | Где |
|---|---|
| Хранение выбора, переключатель для профиля | `frontend/src/background.js` |
| Сфера из машин | `frontend/src/sphere.js` |
| Трубы: рисование, камера, цикл | `frontend/src/pipes.js` |
| Трубы: сетка и рост (чистые правила + тесты) | `frontend/src/pipesGrid.js` |
| Подъём нужной заставки | `mountBackground()` в `frontend/src/main.js` |
| Песочница без входа и без базы | `frontend/dev-background.html` |

Инлайнового скрипта в `<head>`, как у темы и акцента, у фона НЕТ, и это не
забывчивость: тема и акцент красят саму страницу и обязаны встать до первого
кадра, а фон рисует прозрачный канвас поверх того же `--search-bg` — мигать
нечему.

Трубы грузятся ОТДЕЛЬНЫМ ЧАНКОМ по требованию, как игры: у тех, кто оставил
сферу, их в первой загрузке сайта нет вовсе. Показана всегда одна заставка,
вторая скрыта классом — и на скрытом канвасе (нулевой размер) обе
останавливают свой цикл сами, а просыпаются от `ResizeObserver`.

### Почему трубы написаны, а не взяты из three.js

Оригинал (github.com/1j01/pipes) — это three.js: 550 КБ и постоянный
WebGL-контекст ради клубка цилиндров, который на фоне читается силуэтом.
Проекцию и сортировку по глубине сфера рядом уже считает сама, и трубам хватает
того же: **труба — это ЛИНИЯ КРУГЛЫМ ПЕРОМ, а цилиндр из неё делает вторая
линия поуже, сдвинутая к свету**. Чанк вышел 7 КБ вместо 555.

Из плоского пера следуют три вещи, которые нельзя «поправить на глаз»:

- **блик на стыках ВЫТЯГИВАЕТСЯ под соседний отрезок.** Отрезки рисуются по
  одному и сзади наперёд, поэтому круглый торец соседа закрашивает конец
  нашего блика — без вытягивания труба выглядит пунктирной. Тянем ровно на
  полтолщины: столько же занимает торец, значит наружу вылезти некуда;
- **появление и уход клубка гасятся ЦЕЛИКОМ, через CSS-прозрачность канваса**,
  а не `globalAlpha` на кисти. Полупрозрачная кисть складывает каждое
  перекрытие сама с собой: трубы просвечивают друг через друга, а на стыках
  проступают светлые точки. Прозрачностей две (`--pipes-fade` у заставки,
  `--pipes-dim` у вёрстки — на узком экране фон приглушён), и они
  перемножаются: затирать чужое значение никому нельзя;
- **потолок в 500 отрезков — про кадр, а не про красоту.** Каждый отрезок это
  две линии в КАЖДОМ кадре; оригинал растит по отрезку на кадр (шестьдесят
  клеток в секунду на трубу) и за десяток секунд забивает куб. Наш рост
  примерно вчетверо медленнее хода камеры: клубок собирается на глазах.

Камера — то, чего в оригинале нет вовсе: там она стоит и прыгает в случайную
точку на каждой перезагрузке клубка. Здесь она ЕДЕТ вокруг куба непрерывно
(оборот за три минуты) и по ходу цикла понемногу отъезжает: клубок растёт, и
неподвижная камера сперва утыкается в него носом, а потом теряет за краем.
Прыжок остался ровно один — в момент, когда экран уже пуст, и увидеть его
нельзя. Отъезд считается от ВОЗРАСТА клубка, а качание по высоте — от общего
времени: возраст обнуляется на каждом клубке, и высота повторяла бы один и тот
же проход раз за разом.

Правила роста вынесены в `pipesGrid.js` по той же причине, по какой правила игр
живут в `shared/`: это единственное во всей заставке, у чего есть инварианты —
узел не занимается дважды, труба не вылезает за куб, а рост обязан КОНЧАТЬСЯ.
На фоне главной этого не разглядеть, а тестом рядом — можно. Там же
единственное расхождение с оригиналом по правилам: у него труба, упёршаяся в
занятый узел, молча стоит до конца цикла, у нас перебираются все шесть
направлений, и в тупике труба умирает — на её место приходит новая.

**Трубы разноцветные, и это не забытый акцент**: в разноцветности вся заставка,
одноцветный клубок читается как ошибка отрисовки. Акцент никуда не делся — он
красит свечение пространства под канвасом (`--search-glow`). А вот ТЕМУ трубы
слушают дважды: светлотой самих труб (на белом фоне те же тона надо брать
темнее, иначе клубок выцветает в молоко) и цветом ДЫМКИ, в которой тонут
дальние, — она красится тем же `--search-bg`, что и пространство. Сам фон при
этом не рисуется вовсе: канвас прозрачный, тему под ним меняет CSS.

Чайник в шарнирах — пасхалка самого оригинала, и она на месте, но СИЛУЭТОМ:
там это настоящий чайник из Юты, меш на пару тысяч треугольников, и плоским
пером его не нарисуешь. Он не поворачивается вместе с камерой; на размере в
десяток пикселей раз в цикл это не видно, а меш стоил бы отдельной библиотеки.

## Скроллбары: полоса только у страницы целиком

У всего вложенного — списков, окон, панелей — полосы прокрутки нет вовсе.
Осталась она только у страницы (`html`), и это не про красоту.

Раньше `scrollbar-width: thin` стояло на `*`, то есть на каждом вложенном
контейнере. В Chrome это **классическая** полоса: она занимает место внутри
элемента, а её прямоугольную дорожку браузер **не обрезает по
`border-radius`** — у скруглённого блока два угла со стороны полосы
становились прямыми. Это и было видно на карточках и в окнах.

Второй довод — на будущее: полосу рисует браузер ПОВЕРХ всего, что мы рисуем
сами, и внутри стеклянной панели она выглядела бы инородной пластиковой
лентой, которой мы не управляем.

Цена названа честно: во внутренних списках пропадает указание «сколько
осталось». Для них это терпимо — они короткие. У страницы целиком, где
прокрутка идёт на тысячи строк, полоса поэтому и оставлена: там это
единственный намёк на масштаб.

## Выпадающие списки: свои вместо нативных

Нативный `<select>` не красится под тему сайта: в Chrome под Windows попап
списка белый в любой теме, а под каждой ОС он ещё и своей формы и своего
размера. Это соображение было записано в шапке `tagSearch.js`, где по той же
причине уже написан комбобокс для тегов; `frontend/src/select.js` распространяет
его на остальные селекты — станции в записях, топливо и агрегаты в редакторе
машины, станция и фильтр в CRM-панели, поля лида.

**Настоящий `<select>` остаётся моделью, и это главное.** Он прячется, но
продолжает хранить значение и получать `change`. Весь остальной код читает
`.value` и слушает `change` ровно как раньше — правок в местах вызова нет ни
одной. Список пунктов собирается из его же `<option>` в момент открытия,
поэтому догрузка станций с сервера подхватывается сама.

Что ещё стоит помнить:

- **класс селекта переезжает на кнопку целиком.** Все существующие правила
  (`.crm-station-select`, `.lead-select` и прочие) написаны на классах, и так
  кнопка выглядит ровно как выглядел селект, без второго набора стилей.
  Правила, написанные на ЭЛЕМЕНТ (`.filter-row select`), расширены до
  `.filter-row .sel-btn` — иначе кнопка теряет их вид;
- **попап живёт в `<body>`**, а не рядом с кнопкой: селекты стоят внутри окон
  и панелей с `overflow: hidden`, и список, нарисованный на месте, обрезался бы
  их краем. Позиция считается от кнопки и пересчитывается на прокрутке и
  ресайзе, пока список открыт; открывается вниз или вверх — туда, где больше
  места, а высота ограничена расстоянием до края экрана, а не выдуманным
  числом: у станций пунктов сорок;
- **на таче остаётся нативный** (`pointer: fine`). На телефоне системный список
  объективно удобнее любого своего — он крупный, с инерцией и привычный;
- **строка поиска появляется от восьми пунктов.** Ниже она только мешает:
  пролистать глазами пять станций быстрее, чем набрать букву.

### Календарь

`frontend/src/datepicker.js` — то же самое для трёх `<input type="date">` в
записях (дата доски, дата в окне создания, дата при правке). Причина та же:
нативный пикер рисует ОС, под тему он не красится ничем, и рядом с тёмным
окном записи выглядит чужим приложением.

Скрытый `<input type="date">` тоже **остаётся моделью**: календарь пишет в
него значение и шлёт `change`, а дальше работает тот же обработчик, что
работал с нативным пикером — логика смены даты не тронута вовсе, в
`records.js` заменены только три места открытия.

- **на таче открывается нативный** — `showPicker()`, ровно как раньше;
- **неделя начинается с понедельника**, и это не вкус: `getDay()` считает от
  воскресенья, и без сдвига `(getDay() + 6) % 7` весь месяц уезжает на день;
- **ISO-строка собирается вручную, а не через `toISOString()`**: тот переводит
  в UTC, и для Москвы вечер 30-го числа становится 30-м или 31-м в зависимости
  от часа — «сегодня» подсвечивалось не тем днём;
- **сегодня обводится, выбранное заливается** — разными средствами, потому что
  сегодняшний день вполне может быть и выбранным.

## Переключатели: капсула с едущей пилюлей

Группа взаимоисключающих чипов, помеченная `data-seg="имя"`, становится ОДНИМ
переключателем: общая дорожка и пилюля, которая ЕДЕТ между пунктами. Правила —
`frontend/src/segmented.js`, стили — блок `[data-seg]` в `style.css`.

Сейчас это восемь групп: пробег, промывка и тип АКПП в калькуляторе, режим
поиска на главной, даты и сортировка станций в записях, даты в окнах создания
записи и её правки.

Перекраска активного чипа не показывает ПЕРЕХОДА: выбор скачком оказывается в
другом месте, и глазу нечего проследить. Отсюда всё остальное:

- **фон активного пункта рисует пилюля, а не сам пункт** — только так его и
  можно двигать. Цвета при этом те же самые, меняется лишь кто их рисует;
- **внутри дорожки у чипов нет своих рамок**: рамка на каждом пункте спорит с
  рамкой дорожки и рвёт капсулу на отдельные кнопки, а смысл переключателя в
  том, что он один;
- **это JS, а не CSS**: чисто на CSS пилюля возможна только у групп с РАВНОЙ
  шириной пунктов, а «Сегодня / Завтра / Дата» и «Поиск / Теги / Клиент» —
  слова разной длины;
- **форма у всех дорожек одна — капсула**, включая пробег и промывку во всю
  ширину колонки. Им от общего правила нужна только раздача места поровну;
  «этот скруглим, а тот нет» вернуло бы разнобой, ради которого и заводилась
  шкала геометрии;
- **плашке режима поиска её стекло возвращено отдельным правилом**: общее
  `[data-seg]` имеет ту же специфичность и стоит ниже, то есть перекрасило бы
  её из `--glass-*` в обычную панель.

Четыре места, на которых это ломалось, и все четыре неочевидны.

**Геометрию пилюли помним ПО ИМЕНИ группы, а не по узлу.** Записи и калькулятор
на смену выбора перерисовывают свой кусок через `innerHTML`: контейнер вместе с
пилюлей выбрасывается, новая рождается уже на новом месте — ехать неоткуда.
Поэтому `data-seg` несёт имя, по нему помнится последнее положение, и дальше
обычный FLIP: поставить туда, где было, и в следующем кадре отпустить. Группа
без имени работает, просто её выбор переставляется скачком.

**Бордюр дорожки вычитается из положения пилюли.** `getBoundingClientRect()`
возвращает border-box, а `position: absolute; top: 0` отсчитывается от
PADDING-box — от внутреннего края рамки. Без поправки пилюля уезжает вниз и
вправо ровно на толщину рамки, и при отступе дорожки в три пикселя этот один
читается как «подсветка съехала».

**Первое уведомление `ResizeObserver` пропускается.** Он присылает его СРАЗУ
при `observe()` — ничего ещё не менялось, это «вот твой начальный размер». Но
приходит оно раньше кадра, в котором пилюля собиралась тронуться, и ставит её
на конечное место без анимации. Переезд гас, не начавшись, и выглядело это как
«анимация не работает вообще».

**Пилюлю на месте не трогают ВООБЩЕ** (`same()` в `put`). Смена выбора приходит
сразу двумя путями: наблюдателем за классом (микрозадача — трогает пилюлю с
места) и `ResizeObserver` (у активного чипа своя насыщенность шрифта, от неё
меняется ширина дорожки — просыпается в том же кадре). Второй ставил пилюлю НА
ТО ЖЕ САМОЕ место, но с `transition: none`, то есть гасил переезд за миг до
первого его кадра. Раньше спасал порядок — перерисовка ставила пилюлю из
`requestAnimationFrame`, уже после наблюдателя за размером; стоило перерисовке
уйти, и переезд гас каждый раз. Поэтому запись в стиль, которая ничего не
меняет, не делается вовсе.

**Но ВИДИМОСТЬ возвращают всегда, даже когда место то же.** Пока раздел скрыт
(ушли на другую вкладку сайта — там `display: none`), группа меряется нулём, и
`place` гасит пилюлю, чтобы она не висела в углу. На возврате `ResizeObserver`
будит нас с ТЕМ ЖЕ местом — и пропуск записи целиком оставлял пилюлю невидимой
до первого клика по чипам. Пропускать можно переезд, но не `opacity`.

Обработчики кликов при этом не тронуты: они как переключали `.active`, так и
переключают, а пилюля едет следом — за классом следит наблюдатель. Новые группы
подхватывает наблюдатель за документом, поэтому `initSegmented()` зовётся один
раз и его не надо помнить после каждой отрисовки.

### Анимация не ждёт данные

Переключатель дня в записях — тот случай, где это правило пришлось выписать
отдельно. **Выбранный день — факт ИНТЕРФЕЙСА, а не данных**: он известен в
момент клика, и ждать доски ему незачем. А ждал: `switchDate` начинался с
`await fadeOutBoard()`, и первые 150 мс на экране не менялось ничего; на
медленном ответе — пока не приедет доска. Теперь день ставится сразу, шапка
правится точечно (`renderHeaderOnly`), а доска уезжает и грузится за ней.

Второе следствие — в `render()`: **шапка не пересобирается, если её разметка не
изменилась.** Замена узла обрывает переезд пилюли на полпути (новый узел
рождается уже в конечном положении), и приехавшая доска съедала вторую половину
анимации. Сравнивается при этом ПАНЕЛЬ без строки состояния и баннера
(`renderTopBar`): строка тикает каждые несколько секунд, и сравнивай мы шапку
целиком, узлы пересобирались бы постоянно. Строку и баннер правит `patchStatus`.

Отсюда правило на будущее: **то, что известно из клика, показывается по клику.**
Загрузка меняет содержимое, а не подсветку выбора.

Сюда же потом ляжет слияние фигур у стеклянной темы: пилюля и край дорожки —
две близкие формы, а `smin` в шейдере сливает именно такие.

## Правила по коду

- Комментарии и сообщения коммитов — по-русски, как в существующем коде:
  объясняем ПОЧЕМУ так сделано, а не пересказываем строчки.
- Сомнительное совпадение хуже пустого поля — в импорте лучше пропустить
  машину, чем записать вероятный артикул.
- Один сбойный элемент не должен ронять ночной прогон: цикл по машинам/группам
  оборачивается в `try/catch` с предупреждением и продолжением.
