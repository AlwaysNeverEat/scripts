# Как устроен проект (для агентов и для себя через полгода)

Три части в одном репозитории:

- `backend/` — Express API + телеграм-бот в том же процессе;
- `frontend/` — Vite-сайт (записи, карточки машин, калькулятор, админка);
- `userscript/` — Tampermonkey-скрипты для CRM и калькулятора масла;
- `backend/scripts/import/` — конвейер сбора данных (Motul, ROLF, MANN, BIG).

## Прод — СВОЙ СЕРВЕР, а не Supabase и не Render

Актуальная инструкция — **`DEPLOY-VPS.md`**. Всё живёт на одной машине
(`/opt/k-spot`, пользователь `deploy`):

| Что | Где |
|---|---|
| PostgreSQL 16 | контейнер `postgres` (`deploy/docker-compose.prod.yml`), порт только на `127.0.0.1` |
| Backend | контейнер `backend`, слушает `127.0.0.1:3001` |
| Сайт | статика в `/var/www/k-spot`, собирается `deploy/build-site.sh` |
| TLS и раздача | системный nginx на хосте + certbot (`deploy/nginx.conf`) |
| Аватарки | том `avatars` (`AVATAR_DIR=/data/avatars`), не Storage |
| Секреты | `deploy/.env` (см. `deploy/env.example`) |

**`DEPLOY.md` описывает СТАРЫЙ путь** (Supabase + Render + GitHub Pages) и
оставлен как история. Не предлагай команды для SQL Editor Supabase, дашборда
Render, переменных `SUPABASE_*`/`VITE_API_BASE` на GitHub Pages — на этом
проекте их больше нет.

Каталог `deploy/` есть **не во всех ветках** — он появился в ветке переезда
(`claude/api-spot-boot-recording-issue-qqvzan`), с которой сервер и живёт.
Прежде чем советовать `git checkout <другая ветка>` на сервере — проверь, что
`deploy/` в ней есть, иначе рабочая копия останется без скриптов деплоя.

### Типовые операции на сервере

```bash
# обновить код и перезапустить бэкенд
cd /opt/k-spot && git pull
docker compose -f deploy/docker-compose.prod.yml up -d --build

# пересобрать сайт (бэкенд трогать не нужно)
bash deploy/build-site.sh

# применить миграцию
docker compose -f deploy/docker-compose.prod.yml exec -T postgres \
    psql -U carsdb -d carsdb -v ON_ERROR_STOP=1 < db/migrations/0XX_имя.sql

# psql руками
docker compose -f deploy/docker-compose.prod.yml exec postgres psql -U carsdb -d carsdb

# бэкап
bash deploy/backup-db.sh
```

Миграции при первом наливе базы применяет `deploy/_pgcopy.sh`; дальше новые
файлы `db/migrations/*.sql` накатываются руками командой выше. Автоматического
трекера версий нет — миграции пишутся идемпотентными
(`CREATE TABLE/INDEX IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`).

## Импорт данных

Запускается на сервере обёрткой (контейнер переживает закрытие ssh, репозиторий
монтируется внутрь, поэтому пересборка образа не нужна — достаточно `git pull`):

```bash
bash deploy/scrape.sh <имя-скрипта.js> [аргументы]
docker logs -f <имя-скрипта-без-.js>
```

Порядок этапов и назначение файлов — `backend/scripts/import/README-v2.md`.
Коротко: `scrape-motul-all.js` → `scrape-rolf.js` (допуски) → `import-cars.js`
→ `build-enrichment-workset.js` → `scrape-filters.js` (MANN) →
`scrape-big-filter.js` → `apply-enrichment.js`.

Все долгие скрейперы чекпоинтят результат после каждой машины/группы и
пропускают уже обработанное — прогон можно прерывать и продолжать. Ответы
каталогов кэшируются в `data/import/cache/`.

Файлы данных: `data/import/motul-cars.json` (машины Motul; `scrape-rolf.js`
без `--out` дописывает допуски **прямо в него**), `cars-enriched.json`,
`cars-workset.json`, `filters.json`. В git лежат только `.gz`-снимки.

## Пасхалки в поиске

В строке поиска на главной есть ОДНО слово-ключ — `игры` (и `games`). Набранное
целиком, оно не ищет машину, и поиск на нём молчит (ни выдачи, ни «ничего не
найдено» — иначе пасхалка перестаёт быть пасхалкой), а по Enter открывает меню
игр `frontend/src/games.js`: иконка и название, клик запускает игру.

Слово одно на все игры сознательно. Раньше их было по одному на игру, и к пятой
получился список, который надо помнить наизусть, — пасхалка, ради которой ведут
конспект, не работает. Новая игра добавляется строкой в `GAMES` (`games.js`) и
иконкой, а НЕ новым словом в поиске.

| Игра | Иконка | Данные |
|---|---|---|
| Вордле — слово из пяти букв за шесть попыток | `assets/game-wordle.png` | `backend/src/wordle/` |
| Контекстно — угадать слово по смысловой близости | `assets/game-kontekst.png` | `backend/src/kontekst/` |
| Сапёр — классический 18×18 на 50 мин | `assets/game-minesweeper.png` | `backend/src/minesweeper/` |
| Тетрис — стакан 10×20 с мини-топом по рекордам | `assets/game-tetris.png` | `shared/tetris.js`, `backend/src/tetris/` |
| Тройка — матч-3 8×8 на время, мини-топ по рекордам | `assets/game-troika.png` | `shared/troika.js`, `backend/src/troika/` |
| Пасьянс — косынка, мини-топ по времени партии | иконки пока нет (плитка рисует масти) | `shared/solitaire.js`, `backend/src/solitaire/` |
| Бильярд — восьмёрка 1 на 1 и с ботом, таблица по очкам | иконки пока нет (плитка рисует номера) | `shared/pool.js`, `shared/poolBot.js`, `backend/src/pool/` |
| Дурак — подкидной и переводной, комнаты на 2–4, бот трёх уровней, таблица по очкам | иконки пока нет (плитка рисует козырь) | `shared/durak.js`, `shared/durakBot.js`, `backend/src/durak/` |
| Рогалик — карточный забег с колодой, картой узлов и бесконечными циклами, топ по циклам | иконки пока нет (плитка рисует ⚔ ◆ ✦) | `shared/roguelike.js`, `shared/roguelikeContent.js`, `backend/src/roguelike/` |

Модуль игры грузится по клику в меню, а не вместе с ним: девять игр — это девять
чанков со словарями, спрайтом, колодой, физикой и колодой карт. Иконки лежат
уменьшенными до 256px, исходники и скрипт пересборки — `design/game-icons/README.md`.
Игра без своей иконки (сейчас это пасьянс, бильярд, дурак и рогалик) рисует на
плитке значки вёрсткой — поле `blank` в `GAMES`: пустое место на её месте читалось бы как
«меню сломалось».

Первые две устроены одинаково: слово — чистая функция от (id аккаунта, дата
МСК), считает её `backend/src/daily.js`. Своё у каждого, меняется в 00:00 МСК,
**в базе не хранится ничего**, миграций нет. Загаданное слово клиенту не
уходит: браузер шлёт попытку, сервер возвращает раскраску или место. Прогресс
живёт в localStorage под id аккаунта.

Словари обеих игр посчитаны заранее (README в каталогах). Python и модели нужны
только для пересборки, на сервере их нет и быть не должно.

Сапёр к суткам не привязан: поле генерируется заново после каждой победы и
проигрыша, а результаты нигде не хранятся — ни в базе, ни в браузере. Раскладка
мин живёт в памяти процесса (перезапуск бэкенда обрывает начатые партии — это
нормально) и клиенту не отдаётся до конца партии. Зато партия переживает F5:
состояние спрашивается у сервера.

Тетрис, тройка и пасьянс устроены иначе первых трёх, и это осознанно. Партия
считается В БРАУЗЕРЕ, а не на сервере: сапёр — это десяток запросов за партию, а
тут до тридцати действий в секунду (тетрис), партия на время, где каскад надо
показать в том же кадре (тройка), и карта, которая едет за курсором (пасьянс).
Правила целиком в `shared/tetris.js`, `shared/troika.js` и
`shared/solitaire.js` — формы и вращение SRS у первого, тройки, специальные
фишки и время у второго, раздача и «что куда ложится» у третьего, — а окна
`frontend/src/tetris.js`, `troika.js` и `solitaire.js` только рисуют и слушают
ввод. На сервер уходит ОДИН запрос — результат в конце партии, и он проверяется
на правдоподобность (`isPlausibleRun` из того же файла): это защита от мусора, а
не от человека с открытой консолью, и большего мини-топ пасхалки не стоит.

Бильярд стоит особняком у всех сразу, и причина одна: он ПАРНЫЙ. Очко, которое
игрок себе приписал, отнято у живого человека, поэтому грубой проверки «бывает ли
такой результат» тут не хватает — партию ВЕДЁТ СЕРВЕР (`backend/src/pool/`). Он
принимает удар (четыре целых числа: направление, сила и куда поставили биток),
применяет его своей копией правил и хранит получившуюся позицию.

Считается при этом партия всё равно в браузере — у обоих. Физика в `shared/pool.js`
сделана ДЕТЕРМИНИРОВАННОЙ: тот же удар из той же позиции даёт тот же результат в
любом браузере и на сервере, поэтому по сети едет удар, а не шестнадцать шаров, и
соперник видит, КАК они разъехались. Держится это на трёх вещах, ломать которые
нельзя: в ядре физики нет `sin/cos/atan2/hypot` (стандарт не фиксирует их до
последнего бита, и Firefox разошёлся бы с Chrome), вход целочисленный, а пары
шаров перебираются строго по номерам. После каждого удара окно сверяет отпечаток
позиции (`stateHash`) с серверным и при расхождении берёт серверную: молча играть
дальше нельзя — двое видели бы разные столы.

Живая игра вдвоём сделана ОПРОСОМ раз в полторы секунды, а не веб-сокетами: ходят
по очереди, действует один человек, задержки не видно, а сокеты потребовали бы
отдельной настройки nginx (`DEPLOY-VPS.md`) ради того, чего никто не заметит.

Бот (`shared/poolBot.js`) перебирает удары ТЕМ ЖЕ движком: берёт копию позиции,
бьёт и смотрит на результат. Знать больше игрока он поэтому не может. Сложность —
это дрожь руки (случайный угол), а не глупость: слабый бот выбирает тот же лучший
удар, просто хуже его исполняет. Партии с ботом живут только в браузере, сервер о
них не знает и в таблицу очков они не идут — иначе первое место занял бы не тот,
кто обыгрывает людей.

Стол семифутовый (78×39 дюймов), а не турнирный девятифутовый: шар к сукну
крупнее (на экране это разница между «видно номер» и «видно точку»), и партия
короче. Подкрутки, прыжков и заказа лузы нет сознательно — см. шапку
`shared/pool.js`.

У лузы ДВА размера, и путать их нельзя: `POCKET_R` — радиус захвата (шар падает,
когда его ЦЕНТР ближе этого), `POCKET_MOUTH` — вырез в борте, внутри которого
борта для шара нет. Второй ровно на радиус шара больше первого, и рисуется луза
именно по нему — тогда шар пропадает, когда целиком вошёл в неё. Если рисовать по
радиусу захвата и не делать выреза, лунка выглядит вдвое больше своей рабочей
области: шар в неё «влезает», отскакивает от борта поперёк устья и уезжает
обратно. Числа физики (трение, края шкалы силы, отскок борта) подобраны замерами
ДЛИНЫ ПУТИ шара, а не его конечной точки: он отражается от бортов и возвращается,
так что по конечной точке выходит ерунда.

Чужой удар показывается ЦЕЛИКОМ: сначала на столе появляется кий и линия прицела
соперника, потом замах, и только потом едут шары (`showAim` в
`frontend/src/pool.js`). Одинаково для бота и для человека — на вход тот же удар
из четырёх чисел. Без этого соперник выглядит невидимой силой, двигающей шары.

Сукно, борт и кий — КАРТИНКИ (`frontend/src/assets/pool-*.webp`), шары остаются
вёрсткой: цветной круг с номером читается на экране лучше фотографии шара
размером в двадцать пикселей. Лузы отдельной картинкой не рисуются — они
нарисованы в самом борте, и весь стол выравнивается одним действием: внутренний
прямоугольник картинки борта натягивается на игровое поле, после чего все шесть
луз сами встают в свои игровые точки. Отсюда же берутся толщина борта и размер
холста — руками они нигде не заданы. Раскладка исходного листа, замеры и команда
пересборки — `design/pool-table/README.md`.

Размер лузы В ФИЗИКЕ задан КАРТИНКОЙ, а не наоборот: `POCKET_MOUTH` равен
замеренной полуширине выреза средней лузы (3.83"), `POCKET_R` — на радиус шара
меньше. Перерисуют борт — эти числа надо пересчитать, иначе шары начнёт отбивать
от невидимого борта посреди нарисованной лунки.

Дурак отличается от ВСЕХ остальных пасхалок одним: в нём есть ЗАКРЫТАЯ
ИНФОРМАЦИЯ. Тетрис, тройка и пасьянс считаются в браузере целиком — там нечего
прятать. Бильярд считается в браузере у обоих, потому что стол виден обоим, и
сервер лишь сверяет отпечаток. В картах так нельзя: браузер, знающий чужую руку и
колоду, знает лишнее. Поэтому партию с людьми ВЕДЁТ СЕРВЕР, а каждому игроку
уезжает не позиция, а ЕГО ВИД на неё (`viewFor` в `shared/durak.js`): своя рука,
РАЗМЕРЫ чужих рук, стол, отбой и козырь. Сверок отпечатка, как в бильярде, тут
нет и быть не может — клиенту нечего пересчитывать.

Из этого же следует главное правило при правках: «что мне сейчас можно» считают
`attackCards`/`defendCards`/`transferCards`/`canTake`/`canPass`, и все пятеро
берут на вход ВИД, а не позицию. Тем же видом пользуется бот — поэтому он
физически не может подглядеть в чужие карты, а не «мы попросили его не
жульничать».

Движок с самого начала написан на 2–4 игроков и на оба режима, а не «на двоих,
потом расширим»: круг, добор и подкидывание в дураке устроены вокруг «следующего
по кругу», и вкручивать это в готовую игру на двоих означало бы переписать её
целиком. Партия один на один — это тот же код при `seats = 2`. Комнату собирают в
лобби (сколько мест и какие правила), полный стол начинает партию сам, а хозяин
может начать и неполным — тогда мест в партии столько, сколько людей реально
село.

Сложность бота — это ГЛУБИНА СЧЁТА, а не фора и не дрожь руки, как в бильярде:
Новичок кладёт козырную шестёрку вперёд некозырной десятки, Любитель знает цену
козырю, а Шулер вдобавок считает вышедшее (когда колода пуста и играют двое,
«что осталось у соперника» — это вычитание, а не догадка). Отсюда панель
«вышло» в окне: раз сильный бот считает отбой, прятать отбой от человека
нечестно — иначе бот знал бы больше, а не считал лучше. Все три уровня и пороги
подобраны турниром бот-против-бота (`shared/durakBot.test.js` его и стережёт):
Любитель обыгрывает Новичка примерно в трёх партиях из четырёх, Шулер Любителя —
чуть чаще половины, и это честно: счёт карт решает в концовке, а до неё оба
играют одинаково разумно. Числа в боте (брать ли вместо отбоя, подкидывать ли
всё подряд) не «на вкус»: и то, и другое проверялось тысячей партий, и оба раза
осторожный вариант ПРОИГРЫВАЛ.

Ход в дураке ПОКАЗЫВАЕТСЯ: карта летит из руки на стол, побитый розыгрыш уезжает
в отбой, раздача и добор рассыпаются из колоды по рукам, а «бито», «беру» и
«перевод» вдобавок пишутся крупно поверх стола. Без этого стол просто
подменяется — карта исчезает из руки и в тот же кадр лежит на столе, а розыгрыш
пропадает целиком; за столом на четверых понять, что произошло, невозможно.
Считается показ ИЗ РАЗНИЦЫ ДВУХ ВИДОВ (`diffViews` в `frontend/src/durak.js`), а
не из «какой ход мы сделали»: с ботом ход известен, а с людьми с сервера
приезжает позиция, и рассказа о ней там нет — разница же видов есть в обоих
случаях и означает одно и то же. Если разницу объяснить не вышло (вкладка спала,
сервер ушёл на несколько ходов вперёд), показ пропускается: три чужих хода подряд
всё равно смотреть некому.

Единственное неочевидное место в правилах — счётчик простоя (`STALL_BOUTS`). В
переводном двое с пустой колодой могут крутить карты вечно: защитник берёт, на
следующем розыгрыше переводит взятое обратно, второй берёт его же, в отбой не
уходит ничего. Это не теория — партия ботов так и зависла (200 000 ходов без
конца). Шестьдесят розыгрышей подряд без единой карты в отбое считаются ничьей,
как правило пятидесяти ходов в шахматах; честной игрой в этот потолок упереться
нельзя (у случайной, которая берёт куда чаще человека, самая длинная серия была
34).

Рогалик — карточный забег в духе Slay the Spire, и он ближе всего к тетрису с
тройкой: игрок ОДИН, соперника нет, закрытой чужой информации нет — прятать не от
кого, поэтому забег целиком считается В БРАУЗЕРЕ, а на сервер уходит один запрос
с результатом. Сравните с дураком: там сервер ведёт партию не «на всякий случай»,
а потому что браузер, знающий чужую руку, знает лишнее.

Устроен он двумя файлами, и граница между ними жёсткая: `shared/roguelike.js` —
ПРАВИЛА (бой, карта узлов, лут, эскалация), `shared/roguelikeContent.js` —
КОНТЕНТ (27 карт, 5 врагов, 2 босса, 9 модификаторов, 10 мутаций, 6 событий).
Движок не знает ни одной карты по имени: карта — это список эффектов
(«нанести 6 урона», «дать 5 блока», «наложить 3 яда»), и добавляется она строчкой
в контент, а не веткой в коде. Появившийся в правилах `if (card.id === ...)`
означает, что затея сломана.

Разнообразие берётся не из объёма написанного, а из ПЕРЕМНОЖЕНИЯ: пять базовых
врагов × девять модификаторов (ярость, шипы, вампиризм, ускоренный…) × номер
цикла дают сотни разных встреч. Уникальных боссов ровно два на всю игру — босс
отличается не именем, а здоровьем, двумя гарантированными модификаторами и тем,
на каком цикле его встретили. Полсотни нарисованных вручную врагов — это способ
выдохнуться на пятнадцатом.

Бесконечность у забега ДВУОСНАЯ, и обе оси нужны разом. Первая — циклы: пройден
босс, карта генерируется заново, у врагов +35% здоровья и +22% урона за каждый
пройденный цикл. Вторая — колода: точильный камень даёт +1 уровень КОНКРЕТНОМУ
экземпляру карты (два «Удара» качаются независимо), и уровень — это ровный
line-scaling, +30% к числам, одной формулой на весь контент. Без второй оси
забег упирается в арифметику эскалации, без первой — не кончается вовсе.

Отдельно от уровня живут МУТАЦИИ карт: редкий осколок вешает на карту условный
эффект («×2 урона, если у врага нечётное здоровье», «первые N розыгрышей за бой
бесплатны»). Та же мутация повторно НЕ ложится второй строкой, а УМНОЖАЕТ
первую: ×2 → ×4 → ×8. Именно из-за этого удвоения осколки и падают так редко,
причём шанс растёт с циклом: ×8 на восьмом цикле — заслуженный финал забега, на
первом — сломанный баланс.

Намерение врага ВИДНО ДО ХОДА ИГРОКА и показанными числами — с его силой,
ослаблением и множителем цикла. Это не украшение: без него броня ставится
наугад, и вся сборка колоды теряет смысл. Поэтому и подписано намерение словами
(«Бьёт 12»), а не значком меча: половина шрифтов рисует его цветной картинкой, и
число рядом читается как что угодно.

БРОНЯ НЕ СГОРАЕТ и копится от хода к ходу — как в карточных играх с героем, а не
как в рогаликах с одноразовым блоком. Разница принципиальная: сгорающий блок
наказывает за «переставил лишнего», а броня превращает защиту во вложение.
Из-за этого числа защиты в контенте маленькие (защита за энергию заметно меньше
урона врага за ход): иначе выгодно закрыться наглухо и не бить вовсе, бой
перестанет кончаться, а забег превратится в соревнование по терпению — тот же
довод, по которому в тройке кончается время. Здоровье и броня показываются
ЧИСЛАМИ, а не полосами: весь расчёт хода тут в целых числах («бьёт 12, у меня 7
брони и 9 здоровья»), а полоса отвечает только на «много или мало».

Ход игрока — это ЗАЯВКА, а не череда немедленных действий. Карта, которую
вытянули из руки на стол, СРАЗУ стоит энергии, но не делает ничего: ни здоровье,
ни броня не двигаются, пока не нажат «Ход». Тогда стол срабатывает СЛЕВА
НАПРАВО, в порядке выкладывания, и только там видно, что вышло. Смысл в том, что
ход приходится считать в голове заранее — с ослаблением, уязвимостью и бронёй, —
а не подбирать по одной карте, глядя на уже уехавшее здоровье врага. Порядок
карт на столе поэтому тоже решение: «Зеркало» перед «Размахом», «Порча» перед
атаками, «Засада» первой.

Из отложенного розыгрыша есть РОВНО ОДНО исключение, и оно не «для удобства»:
добор, энергия и улучшение карты в руке (INSTANT в `shared/roguelike.js`)
срабатывают при выкладывании. Они меняют не бой, а САМУ ЗАЯВКУ — что игрок ещё
успеет положить на стол; карта, которая тянет карты в конце хода, тянет их в
руку, уходящую в сброс, то есть не делает ничего. По той же причине карта с
`bounce` («Эхо-камень») возвращается в руку не сразу, а в начале следующего хода.

Ход ПОКАЗЫВАЕТСЯ, как в дураке, но проще: карта улетает из руки на стол (и это
честный FLIP — она уже нарисована на своём месте, а мы лишь отпускаем её из
руки), потом по «Ходу» стол загорается карта за картой, над врагом отлетают
цифры, счётчики едут, невыложенная рука уезжает в сброс, и только потом плашка
«Ход врага» и его удар в ответ. Держится это на ЖУРНАЛЕ (takeLog в правилах):
правила считают ход целиком и мгновенно, но пишут каждый шаг — какая карта
сработала (`cast`), сколько прилетело и сколько осталось здоровья и брони, — а
окно проигрывает журнал по событию и рисует счётчики из своей копии, а не из
состояния движка. Оттуда же копии стола, руки и намерения на время показа:
правила к этому моменту уже раздали новую руку и загадали врагу СЛЕДУЮЩЕЕ
намерение, а игрок смотрит на предыдущий ход. В дураке показ вычисляется
разницей двух видов, потому что позиция приезжает с сервера без рассказа о том,
что случилось; здесь правила и окно в одном браузере, и рассказать честнее.

Рука лежит ВЕЕРОМ внахлёст, и поднятую карту выбирает JS (ближайшую к курсору),
а не `:hover`. Причина простая: карты перекрывают друг друга, поднимаясь, карта
уезжает из-под курсора, курсор попадает на соседку — и веер дрожит. Раскладка
(шаг, разворот, размер карточки) считается в окне, потому что зависит и от числа
карт, и от размеров окна: бой обязан помещаться целиком, карту нельзя выложить,
если до руки надо доскроллить.

Перед боссом на карте всегда стоит костёр — один узел на строку, мимо не пройти.
Без него исход боя с боссом решала бы не колода, а то, сколько здоровья случайно
осталось за одиннадцать узлов до него; с ним на костре появляется решение
(отдохнуть или заточить карту).

Числа контента подобраны не на глаз: в `shared/roguelike.test.js` живёт
АВТОИГРОК — простой бот, играющий забег по тем же функциям, что и окно. Он
стережёт две границы: забег обязан заканчиваться (бесконечность — не вечность), а
первый цикл средний игрок должен проходить примерно в двух третях забегов и
никогда не доходить до десятого. Правка баланса «на глаз» ломает обе границы
молча.

Всё случайное идёт через ОДИН генератор с сидом (xorshift32 в правилах): ни
одного `Math.random` ни в правилах, ни в окне. Сид нужен не для красоты — по нему
воспроизводится жалоба «вот на этом забеге сломалось», на нём стоят тесты, и на
нём же однажды сделают забег дня, не переписывая игру.

Забег переживает не только закрытие окна, но и перезагрузку страницы: состояние —
обычный объект без функций, и оно целиком уезжает в localStorage под id аккаунта.
В отличие от тройки, где партия живёт минуты, забег идёт десятки минут, и терять
его от случайного F5 нельзя. Время при этом копится ТОЛЬКО пока окно открыто и
вкладка видима — иначе «полтора часа» в подписи рекорда означало бы «вкладка
висела с ночи».

Графика у рогалика подключается ПО ИМЕНИ ФАЙЛА: положили
`frontend/src/assets/roguelike/strike.png` — и «Удар» нарисован, кода править не
надо (`import.meta.glob` в окне игры). Никакой таблицы «карта → картинка» нет:
имя файла и есть id карты. Карты без файла рисуются вёрсткой — колода
дорисовывается неделями, и смешанная рука это переходное состояние, а не
поломка.

На картинке НЕ рисуются числа и описание: они меняются от уровня и мутаций
(«Удар» 4 уровня с ×4 бьёт совсем не на 7), а описание собирает движок из
эффектов. Шар с числом при этом бывает ТОЛЬКО У АТАКИ: он нарисован на рамке
оружия и означает урон, а блок, положенный на его место у умения, читается как
«столько эта карта бьёт». Что уже стоит в шаре, описание второй раз не пишет, а
длинный текст УМЕНЬШАЕТСЯ шрифтом, а не обрезается рамкой: обрезанная карта
перестаёт объяснять, что делает. Стоимость, главное число и текст кладутся
поверх текстуры в пустые поля рамки — шрифтом Bitter (`frontend/src/assets/fonts/`, SIL OFL): системный
гротеск сайта спорил бы с брусковой антиквой на самой рамке. Что рисовать, каких
размеров, какую рамку брать под атаку и умение и куда попадают числа —
`design/roguelike-cards/README.md`.

Мини-топы — единственное, что пасхалки вообще хранят в базе: таблицы
`tetris_scores`, `troika_scores` и `solitaire_scores` (миграции
`025_tetris_scores.sql`, `026_troika_scores.sql`, `027_solitaire_scores.sql`), по
ОДНОЙ строке на игрока — его рекорд. Историю партий не пишем: топ показывает
лучший результат, а тысячи строк «партия на 300 очков» не нужны никому. Таблицы
отдельные, а не одна общая с колонкой игры: показатели в подписи строки у игр
разные (линии и уровень против ходов, часов и каскада), и общая таблица
неизбежно стала бы набором полей, половина из которых всегда NULL. У пасьянса к
тому же рекорд — МИНИМУМ: там соревнуются временем, поэтому в его таблице `LEAST`
вместо `GREATEST` и `ASC` в индексе.

Туда же относится `roguelike_scores` (миграция `034_roguelike.sql`), с одной
особенностью: рекорд там — ПАРА (пройденных циклов, пройденных узлов). Циклы —
то, ради чего в эту игру играют, но мера грубая: два забега «по два цикла»
отличаются тем, где именно каждый умер на третьем. Отсюда сравнение строк
Postgres в upsert (`(EXCLUDED.loops, EXCLUDED.floor) > (…)`) и составной индекс.

У бильярда в базе не рекорд, а СЧЁТЧИК (`pool_scores`, миграция `028_pool.sql`):
победа — очко. Рядом хранятся и поражения — они не влияют на место, но
показываются («12 / 4»): одно очко за победу поощряет количество, и без второго
числа сыгравший сорок партий обгонял бы выигравшего восемь из десяти. Эло не
берём — в офисе оно только запутает. Там же лежит `pool_games` — партия целиком,
и нужна она ровно потому, что сервер тут арбитр. Брошенную партию можно забрать
себе через сутки без хода соперника, а сдаться — кнопкой: иначе проигрывающему
выгодно просто закрыть вкладку.

У дурака в базе то же самое (`durak_scores`, миграция `033_durak.sql`) и по той
же причине, с одной поправкой из правил: проигравший там ровно один — тот, у
кого остались карты, — а победителей за столом на четверых бывает трое, поэтому
поражение пишется одной строкой, а победы всем остальным. Ничья (вышли разом или
карты пошли по кругу) не пишется вовсе: дурака не было. Партия целиком лежит в
`durak_games`, и игроки там МАССИВОМ, а не колонками `p0`/`p1`, как в бильярде:
место в массиве и есть место за столом, и из него же берётся, кто чей сосед.

Тройка — единственная игра со своей экономикой: таймер идёт вниз, а часы на поле
его продлевают, поэтому очки берутся не с тройки (она стоит 30), а с каскадов и
собранных по пути «штучек» — ракеты за четыре фишки разом, бомбы за шесть,
призмы за восемь. Сложность растёт уровнем: чем больше очков, тем реже сыплются
часы, и любая партия рано или поздно кончается — иначе бесконечный режим
сравнивал бы в топе терпение, а не игру.

Поверх этой экономики в тройке идут МИНИ-ЗАДАНИЯ: в случайный момент приходит
короткое условие со своим таймером («разбить 14 звёзд», «собрать трое часов»,
«довести цепочку до ×5»), а за него дают очки, ×2 на все получаемые очки на
двадцать секунд или секунды в банк времени. Смысл в подмене цели: без задания
матч-3 на время — это поиск любого хода побольше, а с ним ход, который сам по
себе хуже, вдруг становится правильным. За провал НЕ отнимается ничего — поле
игрок не выбирает, в отличие от хода. Правила (условия, награды, зачёт) — раздел
«Мини-задания» в `shared/troika.js`, панель сбоку от поля — `renderQuest` в
`frontend/src/troika.js`; на узком экране панель переезжает НАД полем.

Из заданий следует единственная неочевидная вещь на сервере: границы
правдоподобности (`isPlausibleRun`) считаются с учётом наград — счёт удваивается
под ×2 и растёт на очки за задания, а длина партии — на выданные ими секунды.
Число заданий в партии ограничено паузой между ними (`maxQuests`), иначе «задание
дало девять тысяч» пришлось бы принимать на слово сколько угодно раз.

Шаг цепочки в тройке ПОКАЗЫВАЕТСЯ ФАЗАМИ (`playStep` в `frontend/src/troika.js`):
вспыхивают засчитанные фишки → исчезают → на их месте всплывают очки → сверху
всё съезжает в дырки. Правила считают тот же шаг целиком и мгновенно, поэтому в
DOM до последней фазы висит старая картинка — она и нужна, чтобы показать, что
именно исчезает. Таймер на время фаз СТОИТ: игрок в этот момент не может сделать
ничего, и длинная цепочка (лучшее, что бывает в этой игре) иначе наказывала бы
сильнее всего.

Собирается в тройке не «линия», а СВЯЗНАЯ ОБЛАСТЬ одного вида, внутри которой
есть фигура — линия из трёх или квадрат 2×2. Убирается область целиком, вместе с
прилипшими по краям одиночками: игрок видит на поле пятно одного вида, а не «вот
эти три в счёт, а четвёртая сбоку — нет». По той же причине награду считает ЧИСЛО
убранных фишек области (`ROCKET_TILES`, `BOMB_TILES`, `PRISM_TILES`), а не их
форма: четыре фишки разом — ракета, как бы они ни легли. Пороги бомбы и призмы
подняты (6 и 8) как раз потому, что пятно набирается легче линии. Две фигуры
сильнее своего размера и названы отдельно — пятёрка в ряд даёт призму, а
пересечение линий (угол, Т, крест) бомбу: их строят намеренно.

Если игрок несколько секунд не ходит, окно подсвечивает пару, которую можно
обменять (`findMove` возвращает всегда один и тот же ход на одном и том же поле —
подсказка не должна прыгать).

Фишки тройки — единственная в проекте игровая ГРАФИКА (у остальных пасхалок всё
рисуется вёрсткой и SVG). Тридцать шесть картинок (6 видов × 6 состояний) лежат
одним спрайтом `frontend/src/assets/troika-tiles.webp`, а строка и столбец в нём
считаются прямо из констант `shared/troika.js` — таблицы соответствия «код →
картинка» нет нигде, поэтому **порядок `KINDS` и значения `NONE…CLOCK` менять
нельзя, не пересобрав спрайт**. Исходники и команда пересборки —
`design/troika-tiles/README.md`.

Пасьянс — обычная косынка ПО ОДНОЙ КАРТЕ и с бесконечными перекладываниями
колоды, и это выбрано под топ: соревнуются ВРЕМЕНЕМ, а по три карты со счётом
заходов половина раскладов не разбирается вовсе — в топе сравнивалось бы «кому
досталась разбираемая раздача». Отмены хода нет по той же причине: партия на
секундомере, а отмена превращает её в «тыкаю, пока не выйдет». В базу уезжают
ТОЛЬКО разложенные партии: у брошенной раскладки времени нет.

Секундомер пасьянса идёт, только пока играют: он заводится первым ходом, встаёт
на свёрнутой вкладке и на закрытом окне (партия сохраняется и открывается с того
же места), и ОСТАНАВЛИВАЕТСЯ на кнопке «Сложить» — когда закрытых карт не
осталось, партия уже выиграна, а автосбор это показ, а не игра.

Карты пасьянса — вторая (после фишек тройки) игровая графика: лист 13×4
`frontend/src/assets/cards-8bit.png` плюс отдельная рубашка `card-back.png`.
Строка и столбец в листе считаются прямо из правил (`suitOf` и `spriteCol` в
`shared/solitaire.js`), таблицы соответствия нет нигде, **менять порядок мастей
и достоинств нельзя, не заменив картинку** (туз в листе стоит в КОНЦЕ ряда).
У карт нарисован только верхний слой на прозрачном фоне — белую подложку со
скруглением рисует CSS. Исходники и раскладка — `design/cards/README.md`.

Внутри сапёра есть вторая пасхалка: набранное в окне игры слово `vok` (в русской
раскладке те же клавиши дают `мщл`) включает в панели кнопку «%», а она пишет на
закрытых клетках шанс мины. Считает его `frontend/src/minesweeperOdds.js`
перебором расстановок — **по открытым цифрам и остатку мин, то есть по тем же
данным, что видит игрок**. Это принципиально: раскладку сервер по-прежнему не
отдаёт, и режим не должен превращаться в «покажи мины» — он показывает шансы, с
которыми игрок и так играл. Флажки в расчёт не берутся сознательно: они могут
быть ошибочными, а вероятность, выведенная из чужой ошибки, бесполезна.

## Факультеты (распределяющая шляпа)

В профиле есть тест на факультет Хогвартса — Гриффиндор, Слизерин, Когтевран,
Пуффендуй. Пройти его можно **один раз в жизни аккаунта**, дальше факультет
закреплён: ручки «пройти заново» нет ни у пользователя, ни у модератора, а
вставка результата идёт через `ON CONFLICT DO NOTHING` (миграция
`029_faculty.sql`). Это не настройка профиля, которую крутят, пока не выпадет
любимая.

Где виден результат: плашка перед ником (**сначала роль `mod`, потом факультет**
— права важнее), «подложка» обложки профиля под цвета дома и карточка с
качествами в профиле. В топе по записям строка тоже красится, **но первое место
всегда золотое** — правило `.top-row.faculty-tint:not(.top-row-gold)`.

| Что | Где |
|---|---|
| Описания домов, префиксы, тексты карточек | `shared/faculties.js` |
| Вопросы, шкалы, эталоны, подсчёт | `backend/src/faculty/quiz.js` (+ тесты рядом) |
| Хранение, джойн факультета к спискам | `backend/src/faculty/store.js` |
| API | `backend/src/routes/faculty.js` |
| Окно теста и карточка | `frontend/src/faculty.js`, песочница `frontend/dev-faculty.html` |
| Гербы домов (картинки) | `design/faculty-crests/README.md` → `assets/faculty-*.png` |
| Плашки перед ником (роль + факультет) | `frontend/src/namePrefix.js` — ОДНО место на весь сайт |

Устройство теста и почему оно такое — в шапке `quiz.js`, коротко:

- ответы **не знают про факультеты**. Каждый вариант двигает четыре шкалы
  (смелость, амбиции, ум, верность), а дом выбирается в самом конце ближайшим
  эталоном. Иначе человек на третьем вопросе понимает раскладку и отвечает не
  про себя, а про желаемый результат;
- **веса не уезжают в браузер**: клиент получает вопросы без них, считает
  сервер по сохранённым ответам;
- у каждого вопроса варианты уравновешены (сумма весов по каждой шкале = 0),
  порядок вопросов свой у каждого аккаунта и не меняется между заходами;
- вес у варианта либо **есть, либо нет** (только −1, 0, +1). Полутона —
  «наполнители» ±1 в довесок к основным ±2 — один раз уже сломали тест: ими
  удобно доводить сумму вопроса до нуля, и по уму с амбициями таких довесков
  набралось 86% и 77%, почти все в минус. Первые четверо получили ум от 0 до
  −65, трое из четырёх — один и тот же дом. Тест мерил не характер, а
  скромность;
- черновик помнит **версию опросника** (отпечаток от самих вопросов, миграция
  `030_faculty_quiz_version.sql`): после переписывания вопросов недопройденный
  тест выбрасывается, иначе старые ответы молча уехали бы под новые вопросы;
- вопросы **не про работу** — обычные житейские развилки. Рабочие ситуации,
  выдуманные со стороны, первый же человек с поста узнал бы как фальшь.

Прогресс живёт **на сервере**, а не в localStorage, и ответ сохраняется по
одному сразу (`POST /api/faculty/answer`): тест проходят на работе, посреди
него звонят, вкладку сворачивают — вернуться нужно на тот же вопрос и с другого
устройства тоже.

Правки вопросов и эталонов **обязательно** прогонять
`node --test backend/src/faculty/quiz.test.js`: половина тестов там
статистическая (все дома достижимы, никто не забирает половину людей, характер
по ответам восстанавливается, шкалы не слиплись), и одно неудачное число ломает
их молча. Главный из них — «перекос населения не сгоняет всех в один дом»:
он проверяет не арифметику вопросов, а то, что даже смещённое по какой-то шкале
население расходится по всем четырём домам. Именно этого теста не хватало,
когда тест сломался в первый раз.

## Особенности автомобилей из CRM

Список «этой машине так не делаем» живёт ОДНИМ файлом — `shared/crmQuirks.js`.
Оттуда его берут страница машины (секция «Особенности из CRM»), калькулятор на
сайте и юзерскрипт (плашки на карточках агрегатов), а `shouldDefaultToPartial()`
в `shared/calculator.js` — только следствие этого списка. Новое правило из CRM
добавляется туда, а не копией в UI.

Формулировки: **«аппаратная замена» в CRM = «полная»**. Если аппарат подключить
некуда — нельзя писать «замену не делаем»: частичную делаем всегда, и текст
правила обязан это говорить, иначе оператор откажет клиенту целиком (тест
`crmQuirks.test.js` это проверяет).

## Подбор масла: три источника требований, и они не спорят

Разбор и обоснование — `docs/DOPUSKI.md`. Коротко, что откуда берётся:

1. **Допуска машины** (`car_approvals`) — это паспорт РЕКОМЕНДОВАННОГО МАСЛА, а
   не требования мотора: у 95% машин там допуска трёх и более чужих марок.
   Значение имеют только родные марке (`shared/approvals.js`).
2. **Продукты Motul по этой машине** — второй источник, дополняет первый.
3. **Правило «марка + годы + топливо»** (`shared/oemRules.js`) — для машин, у
   которых допусков нет вовсе (каждая пятая).

Граница между ними жёсткая, и её нельзя размывать: правило применяется как
требование ТОЛЬКО там, где родного допуска нет ни в списке, ни у Motul, — они
никогда не работают одновременно. Единственное, что правило говорит всегда, —
есть ли у машины сажевый фильтр: это железо, а не строка в списке.

Новое знание о требованиях завода добавляется в `oemRules.js` строкой допуска
из справочника `approvals.js`, а не отдельной веткой в подборе.

## Осторожно: обозначения фильтров

В данных и в импорте (`extractFilters` в `scrape-filters.js`, `shared/crmAnalyse.js`):

- `vf` — **воздушный** (артикулы MANN `C …`);
- `mf` — **масляный** (`W …`, `HU …`);
- `sf` — салонный (`CU …`, `CUK …`, `FP …`).

Подписи в скобках на карточке машины (`frontend/src/carPage.js`) и в
калькуляторе юзерскрипта им противоречат — им верить нельзя, эталон здесь.
Прежде чем писать любой код, который переносит или сравнивает фильтры, сверься
с этим списком: перепутанное поле означает неверный артикул у оператора, а это
хуже пустого поля.

## Правила по коду

- Комментарии и сообщения коммитов — по-русски, как в существующем коде:
  объясняем ПОЧЕМУ так сделано, а не пересказываем строчки.
- Сомнительное совпадение хуже пустого поля — в импорте лучше пропустить
  машину, чем записать вероятный артикул.
- Один сбойный элемент не должен ронять ночной прогон: цикл по машинам/группам
  оборачивается в `try/catch` с предупреждением и продолжением.
